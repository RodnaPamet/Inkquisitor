# 2026-11-26 — 4.1 Fact layer and retrieval (D27)

**Commit:** uncommitted (branch `wip/4.1`, cut from `main` at `2768214`)

4.0 drew facts from the author's uploaded drafts and let the author confirm
them. 4.1 extends the same fact model to the bible itself: every accepted
version of an element or a relation is read for facts in the background, the
facts count at once, a restatement adds provenance rather than a twin, and a
contradiction is proposed — never applied — for the author to settle on the
Facts page. Elements, facts and answers gain embeddings, and the interview's
context is assembled under one budget and searched by meaning as well as by
words, with the book's allowed set inside the vector query.

## Design

```
bible save (any writer) ── version INSERT ──▶ trigger: BibleFactExtraction PENDING (+ EmbeddingTask for the element)
                            (same transaction: a rollback leaves neither)

every minute: fact-layer-dispatch
  extractions   only if a call can be made and a record mounts (D11)
                due = PENDING settled 20 s | STOPPED with nextAttemptAt ≤ now | QUEUED/RUNNING stale 30 min
                (discovery outside RLS, ids only) → markQueued in its workspace → enqueue `bible-facts` (ids)
  embeddings    each EmbeddingTask (element changed, fact written, answer given): read the row now,
                embed in the deployment (D8), upsert through the 2.0 store, delete the task

bible-facts job: executeBibleFactExtraction({ workspaceId, extractionId })
  look      QUEUED? book live? subject there? newest version of it? (else SKIPPED SUPERSEDED: a run of autosaves
            is read once) author still bible.edit? (else SKIPPED, nothing spent) kill switch / no key / D11 → STOPPED
  claim     QUEUED → RUNNING; render the version and its BASELINE (the entry's newest DONE extraction);
            changed sections; live facts about the subject(s) (bible + the book library's confirmed source facts)
  call      nothing changed → no call (NO_CHANGE). Else chargeModelCalls (waited ≤ 60 s), ONE fast call over the header
            and the changed sections, the live facts numbered; its cost on the row in its own transaction
  persist   lockBook → validate (4.0's rules on the text SHOWN, + the entry's own) → claim keys → resolveFacts:
            insert new claims CONFIRMED/automatic, provenance for restated, proposals for contradictions (RULE/MODEL)
            and NO_LONGER_STATED → DONE → audit last

Facts page: FactProposalsPanel — older/newer, both quoted, with their origin → INVALIDATE | KEEP_BOTH | REJECT
interview round: claim (lexical context, or none if an embedder exists) → embed query outside every tx →
                 one tx: assembleSourceContext(query) → generate
```

## Decisions

- **An outbox written by a trigger, drained by a minutely dispatcher.** The
  owner allowed an outbox or an after-commit enqueue. A trigger on each version
  table writes the row in the version's own transaction, so every writer — the
  versioned save, a restore, the import, enrichment and research acceptance,
  the order move, and any future one — is covered without touching the bible's
  write path, and a rollback leaves nothing by construction. An after-commit
  enqueue from `recordVersion` would have opened a Redis connection from every
  test and request that saves the bible, and still needed a sweeper for an
  enqueue lost after commit. The cost is latency: up to the 20 s settle plus a
  minute.
- **Coalescing.** A version's extraction is SKIPPED when a newer version of the
  same entry exists: autosave writes a version every few seconds, and only the
  newest is read. Combined with the settle time, a burst of edits is one call.
- **Incremental: only what changed is sent.** The model sees the entry's header
  and the sections that differ from its BASELINE (the newest version that was
  extracted). An unchanged field is never re-read, so a fact it stated is never
  re-worded into a near-duplicate or a false contradiction, and the call is
  smaller. A cleared field is not sent (it states nothing); what it stated is
  caught by NO_LONGER_STATED.
- **Dedupe is code (owner).** The claim key is the owning entry, the predicate,
  the subject element, the object's name key and the statement's content words
  with its polarity; keyed with the workspace subkey, never a plain digest. One
  live fact per key in a book is a partial unique index. The model is NOT asked
  for duplicates (graphiti's `duplicate_facts`), only for contradictions.
- **Contradiction: proposed, by rule or by the model.** The rule is narrow on
  purpose (AGE, LOCATION, OCCUPATION, PLACE_TYPE that plainly differ at an
  overlapping story time): a ROLE or a WANT can hold several values. The
  model's judgement is checked (the fact must have been shown, same subject
  element). Both only propose; the author decides. A fact whose quote is gone
  from its own entry is proposed as NO_LONGER_STATED, so a cleared field does
  not keep answering the frontier without the author's say; a fact the version
  contradicts is not also proposed as no longer stated.
- **Ownership and deletion.** A bible fact belongs to its element (or its
  relation): deleting it cascades the facts, their provenance and proposals.
  Versions are append-only and stay with the book. A relation's facts go with
  the relation: removing it retracts what it stated (there is no relation
  restore; the undo toast acts before the delete). Facts about a deleted OBJECT
  element keep their text, the link set NULL.
- **Series facts are never resolved against.** A series source's fact is shared
  by every book that opted in; invalidating it for one would change others.
  Only bible facts and the book's own library's confirmed facts are.
- **No ANSWER kind.** An answer reaches the fact layer through the version that
  accepted it (`sourceAnswerIds`); a fact drawn from an unaccepted answer would
  be model output treated as canon (rule 1).
- **The query embedding moves after the claim.** With an embedder, the claim no
  longer reads the context; the round embeds its query (the scope's names and
  targets) outside every transaction and reads the context in one transaction
  more. The latency test now counts that: three transactions without an
  embedder, four with one, one embedding before the first call, which still
  follows exactly one model call.
- **The allowed set in the vector query.** `within` joins the source row
  (`SourceChunk` by its source, `StoryFact` by its book or source, live and
  confirmed) inside the ranking query, under the caller's RLS; the hits are
  still read back through the set as a second line. The in-process backend has
  no rows to join and refuses the filter.
- **Answers' vector guard takes no lock.** `Answer` is append-only, app_user has
  no UPDATE on it, and `FOR KEY SHARE` needs one; a plain existence check guards
  it (an answer is deleted only with its session's cascade).
- **`WORLD_RULE`'s RULE is the only widening of the predicate table.**
- **#57.** Items 1 (embed what has no vector, every pass), 2 (REPEATS_PROMPT —
  only the prompt refusal the text causes, a passage repeating the prompt, is
  marked read; any other prompt error stays a chunk failure for a resume), 3 (`within`), 5 (cost counted in its own transaction when the
  write fails) and 6 (the worker aborts running jobs on shutdown) are fixed.
  Item 1 retries on a resume; an ingestion that extracted every chunk and only
  failed to embed is still DONE and not resumable (4.H). Items 4 and 7 are
  4.H's.
- **Backfill.** Versions saved before 4.1 have no outbox row; 4.H item 5 is
  their backfill.

## Review

Five defects found in review, each with a test in `tests/integration/fact-layer.test.ts`
("review of 4.1"):

- **An older version persisted after a newer one.** The superseded check ran only
  before the claim. A version whose call was still running when a newer version of
  the same entry was saved, extracted and persisted then wrote its stale facts, and
  the resolve proposed the NEWER facts for invalidation by them (and could mark them
  NO_LONGER_STATED). `persist` now asks again, under the book's fact lock, whether the
  version is still its entry's newest, and ends it SKIPPED SUPERSEDED (its cost
  already counted) when not.
- **A dispatcher tick could steal a live claim.** `markQueued` re-queued a row in any
  of PENDING, STOPPED, QUEUED or RUNNING, whatever discovery had seen: a tick that
  overlapped another reset a row the other had just queued and a worker had claimed,
  so its call was paid for and thrown away. The mark now asks the same due window
  as discovery (`dueWhere`), in the same statement.
- **A save during an element's embedding was lost.** A repeat of a waiting task did
  nothing, so the dispatcher's delete took the task the newer save had hit, and the
  vector stayed the old text's. `EmbeddingTask.generation` (migration
  `20261126120000_embedding_task_generation`) is bumped by each repeat, and a task is
  deleted only at the generation that was read.
- **The vector path ignored a book's override.** A series fact the book overrode,
  found by the facts search, reached the context in the series' words; it is now the
  book's override text (`OVERRIDE`), as the scope's facts already were. The read-back
  also asks CONFIRMED, as the query does.
- **An invalidated source fact carried its decision.** A re-upload carries the old
  version's decisions; a fact the author had invalidated still read CONFIRMED and
  came back live in the next version. `listDecidedForSource` leaves invalidated facts
  out, so the same claim is PENDING for the author.
