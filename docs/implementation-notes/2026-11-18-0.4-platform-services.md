# 2026-11-18 — 0.4 Platform services and tooling

## Design

Phase 0.4 lifts inflect-compliance's product-neutral platform services at
commit `5528464fc54a8681956f3b9ce23ca9c075f0420e` and wires them so that
Phase 0.3 (authentication, workspaces, RLS) can plug in without reshaping
them.

```
request ─▶ src/middleware.ts (edge)
             ├─ /api/auth/**       auth tier  (IP + UA hash; 10/30/60 per min)
             ├─ GET /api/** else   read tier  (workspace slug, IP, userId|anon; 120/min)
             └─ x-request-id stamped on request and response
         ─▶ route handler wrapped in withApiErrorHandling (node)
             ├─ observability context (requestId, route; workspaceId/userId from 0.3)
             ├─ api.request span, request metrics, start/end log lines (no body)
             ├─ mutation tier on POST/PUT/PATCH/DELETE (60/min per IP[, user])
             └─ typed errors → { error: { code, message, requestId } }

enqueue(name, payload) ─▶ BullMQ queue "inkquisitor-jobs" (Redis)
                           ─▶ scripts/worker.ts → createJobWorker
                                 ─▶ executorRegistry.execute → executor (runJob)
                                 ─▶ on completed: heartbeat key (TTL 8 min)
```

- **Observability.** pino with one redaction list (`redaction.ts`) shared by
  the Node, worker and edge loggers: credentials plus the author-text names
  `text`, `answer`, `content`, `body` (roadmap rule 4), matched by name,
  case-insensitively, at any depth on both loggers (pino's literal `redact`
  paths are only a fast path; `formatters.log` and a wrapped `child` run the
  same walk as the edge logger). An error's message leaves the process only
  when it is an AppError's (`safe-error.ts`): any other error reaches a log
  line, a span or Sentry as its name, code and stack frames. OpenTelemetry (off unless
  `OTEL_ENABLED=true`) and Sentry (off unless `SENTRY_DSN`) initialise from
  `src/instrumentation-node.ts`; Sentry's data collection is pinned off and
  `scrubEvent` drops bodies, cookies, auth headers, query strings and IPs.
  Graceful shutdown runs bounded stages (connections, OTel, Sentry) that a
  throw or a hang in one cannot skip, after Next's HTTP drain and before the
  process exits.
- **Rate limiting.** Three tiers. The edge tiers count in Upstash only when
  both REST variables are set, otherwise in an in-process fixed window
  (`window-store.ts`); the mutation tier is inflect's in-process sliding
  window. Every store sweeps lazily on a caller's turn; nothing in `src/`
  calls `setInterval` (guarded).
- **Storage.** Local (default) and S3 providers, workspace-scoped object keys
  with an ownership assertion, upload limits, and the clamd INSTREAM scanner
  with the strict / permissive / disabled download gate.
- **Mailer.** Console sink (logs counts and recipient domains only), SMTP via
  nodemailer when `SMTP_HOST` is set (TLS required: implicit on 465, STARTTLS
  on any other port; only a loopback catcher outside production may skip it),
  a stub for tests.
- **Jobs.** Typed queue, an executor registry that ships empty of product
  jobs except the no-op `heartbeat`, schedules registered on every worker
  boot, a cron `scheduler.tick` for hosts without the worker, trace context
  carried across the queue, and an esbuild bundle (`dist/worker.mjs`) plus a
  heartbeat healthcheck.
- **Probes.** `/api/livez` (process up) and `/api/readyz` (PostgreSQL and
  Redis, each raced against 2 s, 503 naming the failure with a fixed error
  vocabulary) beside the existing `/api/health`.
- **Production configuration.** Every new variable is optional with a safe
  development default. `src/lib/startup-checks.ts` lists what production
  cannot run without (database, authenticated Redis, an S3 bucket when S3 is
  chosen, a persistent `FILE_STORAGE_ROOT` when it is not, a virus scanner
  unless scanning is disabled, both or neither Upstash variables); the web
  tier and the worker both exit 1 on any of it,
  even with `SKIP_ENV_VALIDATION` set. The env schema repeats the Redis rule.
  Both skip their production-only rules during `next build`
  (`src/lib/build-phase.ts`), which is not a running production process.
- **Tooling.** The local ESLint plugin with five generic rules, the secret
  scanner (husky pre-commit, a whole-tree unit guard, a CI gate), CI jobs
  Security / CodeQL / Docker beside the original four, a release workflow, and
  a single Starlight help site publishing `docs/user/` only.

## Decisions

- **Upstash is opt-in by configuration, not by mode.** inflect defaults
  `RATE_LIMIT_MODE` to `upstash` and falls back to memory when the client
  cannot be built. Here the fall-back is the rule (`usesUpstash()`), so a
  development machine needs no setting; production is told, by the startup
  check, when only half the Upstash pair is set.
- **The edge tiers were given a lazy sweep.** inflect's two edge memory
  stores never evicted; the shared `MemoryWindowStore` does, on a caller's
  turn, at most once a minute.
- **The read tier covers every `/api/` GET**, not only `/api/t/<slug>/`, and
  keys on a `/api/w/<slug>/` workspace segment when present. The workspace
  URL shape is Phase 0.3's to fix; the key function is the one place to
  change. `userId` is a parameter (null today) for the same reason.
- **Middleware, not proxy.** Next 16 prints a deprecation notice for
  `middleware.ts`; inflect still runs it, and the edge tiers are written for
  that runtime. Moving to `proxy.ts` (Node runtime) is a one-file change when
  Phase 0.3 lifts inflect's session gate.
- **Instrumentation is split** into `instrumentation.ts` (an `=== 'nodejs'`
  dynamic import) and `instrumentation-node.ts`, because the edge compile
  otherwise tries to bundle BullMQ (and its optional `pg`) and fails.
- **`instrumentation-node.ts` statically imports only the refusal**
  (`startup-checks`, `build-phase`, neither of which loads `@/env`) and
  dynamic-imports the services after it. Every service imports `@/env`, whose
  schema throws at module load; Next treats a throw from the instrumentation
  hook as "Failed to prepare server" and then keeps the process up answering
  500 on every route, `/api/livez` included — a live-looking server that
  cannot serve. So the refusal runs first, and a production server whose
  services still fail to load (any other invalid variable) prints
  `[startup] FATAL` and exits 1; development and `next build` rethrow. The
  worker needs no such ordering: it is a plain Node process, and a throw at
  module load already exits it 1.
- **Storage defaults to local** (inflect defaults to S3): development needs no
  bucket. Production on local storage is a legitimate deployment on a
  persistent volume, but its development default (a folder under the OS temp
  directory) is lost on restart, so production refuses to start on local
  storage unless `FILE_STORAGE_ROOT` names the volume.
- **A signed download URL lives 300 s at most.** The S3 provider defaults to
  `SIGNED_DOWNLOAD_URL_TTL_SECONDS` and caps a caller's `expiresIn` at it
  (inflect enforces the number in its download route; here the provider does,
  so it holds before any route exists). Upload targets state their 3600 s in
  the same module rather than inheriting it.
- **A virus scanner is required in production** unless scanning is disabled
  on purpose. With the default strict mode and no scanner, every upload would
  be stored and never downloadable.
- **The worker is a function plus a thin process.** `createJobWorker` is the
  processor, so the integration test runs the real one against a real Redis
  on a queue of its own; `scripts/worker.ts` only boots, registers schedules
  and handles signals. `npm run worker` passes `--env-file-if-exists` for
  `.env` and `.env.local` (tsx reads neither, and the schema requires
  `DATABASE_URL`); the production bundle reads the real environment.
- **An enqueue fails rather than hangs.** BullMQ waits for its first Redis
  connection with no limit, so a route that enqueued during an outage never
  answered. The producer connection has no offline queue and the add is
  raced against `ENQUEUE_TIMEOUT_MS` (5 s), failing with a 502 AppError. An add
  that lands after its timeout still runs, so executors stay idempotent on the
  rows they name. Only the Worker's connection keeps
  `maxRetriesPerRequest: null`.
- **The shutdown handler defers Next's `process.exit`.** `next start` calls
  `process.exit(143)` as soon as its own HTTP drain ends, never waiting for
  another SIGTERM listener, so the OTel and Sentry flushes were cut short.
  Taking the signal over (`NEXT_MANUAL_SIG_HANDLE`) would mean reimplementing
  the HTTP drain without access to Next's server. Instead the handler
  replaces `process.exit` once a signal arrives: Next's call, made after the
  drain, runs the stages and then exits with Next's code, and a fallback
  timer (`SHUTDOWN_HTTP_DRAIN_MS`) does the same if no call comes. The
  connections stage therefore runs after the last request, not beside it.
  Worst case drain plus stages is 18 s, so a container needs a stop grace
  period of 20 s.
- **Only an AppError's message is reported.** A Prisma validation error renders
  the failed call's arguments, a `JSON.parse` error quotes its input, and
  redaction matches field names, never a value inside a message. So every sink
  (logs, span status and exception events, Sentry, the executor registry's
  failure reason) goes through `safe-error.ts`, which keeps a non-AppError's
  name, `code` and stack frames and withholds its message. Sentry's
  `beforeSend` applies the same rule to events its own instrumentation
  caught. The cost is debuggability of third-party errors, which the code and
  the frames mostly recover.
- **The job payload is never logged.** inflect logs a reduced projection of
  it; here a payload names rows by id and the log line carries name, id,
  attempt and duration only.
- **The mailer logs no part of the message** an author could have written:
  recipient domains and character counts, never the subject, body or address.
- **`no-raw-prompt-logging` applies to all server code under `src/`** and
  `scripts/`, not a single path as in inflect: author text is everywhere in
  this product. Components are excluded (they render the author's text to
  the author). `captureError` is a sink; inflect's audit-stream and
  automation sinks are not carried.
- **CodeQL always analyses, keeps its SARIF as an artifact, and gates on it.**
  The upload to code scanning happens only when the repository variable
  `CODE_SCANNING_ENABLED` is `true` (the upload needs code scanning enabled),
  and `analyze` never fails its job on what it finds, so without a gate the
  check was green whatever it found and, by default, the findings went
  nowhere. `scripts/sarif-gate.js` fails the job on an unsuppressed security
  result of `security-severity` >= 7.0 or level `error`, and on an empty
  results folder; quality results are reported and never block.
- **Trivy runs in the Docker job**, scanning the loaded image, rather than in
  a separate job fed by an artifact as in inflect: one job, one image, no
  tarball hand-off. It carries inflect's `timeout: 15m`: Trivy's own 5-minute
  deadline is not the job's, and inflect's gate failed twice on it with no
  CVE found.
- **CI groups a push by commit.** Keyed by ref, every main commit shared one
  concurrency group, and GitHub cancels a waiting run when another queues
  behind it, so some main commits never got their checks.
- **The release runs on GITHUB_TOKEN alone** by not committing back to main:
  commit-analyzer, release-notes-generator and github only, comments off, so
  the token needs `contents: write` and nothing else. The version lives in the
  tag and the GitHub Release; there is no CHANGELOG.md commit and
  `package.json` stays `0.0.0`. semantic-release and its plugins are installed
  with `npm ci` from `release/package-lock.json`, not resolved by `npx` at run
  time: the job holds a token that can push tags, so every package it runs is
  the locked version. The tree stays out of the application's, and the
  checkout does not persist the token. The release tree is not under
  `npm audit`: its findings are in the npm CLI that semantic-release bundles
  for a publish plugin this configuration does not load.
- **The docs site is one site**, at `/Inkquisitor/`, whose allowlist always
  publishes `docs/user/index.md` and refuses anything outside `docs/user/` and
  the internal docs by name. An entry must be a plain path in normal form (no
  `..`, `.` or empty segment, no backslash), NEVER_PUBLISH is checked on the
  normalised path, a symbolic link is never read, and a page is never written
  outside the content folder: a prefix check alone let
  `docs/user/../ROADMAP.md` through. inflect's UI-label tokens, route checks and
  generated reference pages are not carried: there is one page.
- **Logs are silent under Jest** (`LOG_LEVEL=silent` in `jest.setup.js`);
  suites that assert on log lines build a logger against a capturing stream,
  with the production options.
- **Integration tests use Redis logical database 14** and a per-run queue
  name, so they never meet a dev server or worker sharing the Redis.
- **`next build` is exempt from the production-only rules, and nothing else
  is.** The build runs as `NODE_ENV=production` and imports every route
  module to collect page data, so the schema's REDIS_URL rule refused a bare
  local build (`Failed to collect page data for /api/readyz`) although no
  runtime secret exists or is needed at build time. Next sets
  `NEXT_PHASE=phase-production-build` before it starts the page-data workers
  and never at `next start`; `isNextProductionBuild` matches that exact value,
  and both the schema rule and `productionConfigProblems` return early on it.
  The built server still refuses to start without an authenticated Redis.
  The alternative, requiring `SKIP_ENV_VALIDATION=1` (or a real Redis
  password) for every local build, put a production secret's shape into a
  developer's build step for no protection.
