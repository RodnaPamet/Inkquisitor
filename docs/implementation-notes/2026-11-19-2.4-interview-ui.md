# 2026-11-19 — 2.4 The interview experience (UI)

**Commit:** uncommitted (branch `wip/2.4`, cut from `main` at `1e002d4`: Phase 1,
2.0, 2.1 and 2.2). Built against 2.2's API; 2.3 (dials, several personas,
defaults, packs) was built in parallel and reaches the UI through one seam
(below).

The roadmap's 2.4: "Enrich" on an element, or "Grill me" on a kind or the
whole book, opens a setup Sheet with a one-line preview of each setting, then a
focused page: the round's questions as cards with the control their kind
takes, the recommendation as one click, Skip, Decide later and "Ask me this
differently"; questions stream in; a side panel shows the targeted fields
filling as answers arrive; keyboard first; resumable and autosaved per answer;
stoppable at any time.

## Design

```
ElementPage "Enrich" ─┐                     (bible.edit only; a reader gets no button)
BookBoard "Grill me" ─┼─► InterviewSetupSheet ──► /interviews/new?<setup>  (APP_ROUTES.newInterview)
kind card "Grill me" ─┘     setup.ts (THE 2.3 SEAM)          │
                                                             ▼
                     InterviewSession ── useInterviewStream ── POST …/interviews/stream
                       │  started → history.replaceState(/interviews/<id>)     (or …/:id/rounds/stream)
                       │  planned → RoundFieldsPanel (keys only, all waiting)
                       │  thinking / draft (read-only DraftCard) / checking
                       │  committed → QuestionCards (the only answerable questions)
                       ├─ QuestionCard ── answer / skip / decide-later / rephrase (2.2 routes + one new)
                       ├─ Finish round ── close (skipUnanswered) ──► next round stream
                       └─ Stop ── stop (every answer kept) ── stop reason worded by code
```

### The streaming design

2.2 persists a round ATOMICALLY: claim it under the session lock (GENERATING),
call the model outside every transaction, then write every question and open
the round in one transaction. 2.4 keeps that exactly and streams around it:

- **Drafts before the commit, answerable only after it.** `produceRound` takes
  an observer (`RoundObserver`): it is told when each generation call starts
  and each call's candidates once code has VALIDATED them. The usecase turns
  those into `thinking` and `draft` events. A draft has no id and no control;
  deduplication, the pack fallback and the persist can still drop or renumber
  it. Only `committed` carries the round as stored (ids, positions,
  recommendations), and the client replaces every draft with it. An observer
  is told, never asked: a throw from it is swallowed, so it cannot change a
  round.
- **Granularity is a call, not a token.** `callStructured` already streams
  from the SDK (`client.messages.stream`, then `finalMessage()`), and exposes
  no partial output; adding a partial-JSON path would be a second way to read
  model output, shown before the guard's verdict on it. So a draft appears
  when its call has returned, been guard-checked and validated: with 2.2's one
  persona that is the whole round at once (after the `planned` fields and the
  `thinking` line), with 2.3's personas it is persona by persona. No new SDK
  path; nothing shown that the guard or validation would drop.
- **Refusals before the stream are JSON, events after it.**
  `interviewStreamResponse` (`src/lib/interview/stream-response.ts`) starts the
  usecase and waits for the first of: the usecase saying it is under way
  (`sink.ready()` — after the claim commits, and for a start after the
  session row exists) or the usecase settling. A throw before that rethrows to
  `withApiErrorHandling`: 400, 403, 409 ROUND_OPEN, 503 AI_UNAVAILABLE are the
  ordinary error envelope, with nothing written. After it, the outcome is
  `committed` or `refusal` (a code, never a message), then always `done`.
- **Cancellation frees the server (2.H item 4).** The request's abort, or the
  reader cancelling, aborts the sink's signal. It reaches the model call in
  flight (`produceRound` hands it to `generateCandidates`, which passes it to
  `callStructured`), no further call is made, and `generateClaimedRound` sees
  the abort and abandons the round: FAILED, its tokens charged, NO question
  written, the session left ACTIVE (no stop is recorded: nothing about the
  session stopped). The next round resumes it.
- **Route conventions.** Both stream routes are
  `withApiErrorHandling(requirePermission('bible.edit', …))`, so they are
  rate-limited as mutations and covered by the authorization tests (signed
  out 401, stranger 404, READER 403). The events carry author-derived text to
  the author's own browser and are never logged. The CSP needs nothing new:
  the stream is a same-origin `fetch` (`connect-src 'self'`).
- **A new session's address at once.** The setup sheet navigates to
  `/interviews/new?<setup>`, whose page starts the stream; the `started` event
  carries the session id and the page `replaceState`s its own URL to
  `/interviews/<id>`, so a reload resumes the session instead of starting
  another. The start runs once (React's development double mount is guarded:
  the unmount's cancel is deferred and cleared by the remount).

### The stubbed-model E2E

The E2E server runs `next start` (`NODE_ENV=production`) with no key and
`AI_DISABLED=1` (2.2's decision), and the 2.2 spec expects that. A full session
needs a model, so a SECOND E2E server runs the same build with
`AI_MODEL_STUB=1` (`tests/e2e/stub-server.ts`, `E2E_PORT + 2`):

- **What the stub is.** `src/lib/ai/model-stub.ts`: a `fetch` that answers
  Messages API requests from what the request carries (the fenced `targets.N`
  blocks, the kinds the system prompt allows, a `previous-wording` block for a
  rephrase), one neutral question per target, SSE-streamed. `clientForRun`
  hands it to the SDK in place of the network — the same seam tests use — so
  the real request builder, fence, guard, messages-only middleware (still
  checking the pinned origin), stream parser, validation, ceiling and
  `AiCallLog` all run. It names no host and loads no SDK.
- **Refused in a real production configuration.** `stubModelProblems`, part of
  `aiConfigProblems` and so of the start-up check both the web tier and the
  worker enforce: in production the stub needs `APP_URL` AND `NEXTAUTH_URL` on
  a loopback address (a real deployment has a public `APP_URL`, which links
  are built from); anywhere, it is refused beside `ANTHROPIC_API_KEY`
  (`stubModelActive` also lets a key win in development); `AI_MODEL_STUB` must
  be `1` or unset; every start with it on logs `[startup] WARN`. Proved by
  `tests/unit/ai/model-stub.test.ts` and by `production-refusal.spec.ts`
  starting the real build with the stub and a real host: it exits 1 naming
  the stub.
- **Packs on the stub server (D13, owner decision 2026-11-20).** After 2.3
  merged, the stub server met D11's mount gate: production mounts a pack only
  on a real model's record, and every committed record is structural, so every
  interview there was 503 PACKS_NOT_MOUNTABLE. The decision: the loopback-only
  stub mode (`loopbackStubMode`, `model-stub.ts`: the stub on, no key, both
  addresses loopback) also accepts structural records, decided in ONE place,
  `packRecordModeOf`. The start-up check holds any structural mode to a
  loopback test server independently of that rule (a FATAL beside a real
  host) and says so at every start (WARN). The matrix NODE_ENV × stub ×
  addresses (spoofs included) × provider key × record kind is
  `tests/unit/interview/record-mode-d13.test.ts`, through the real mount gate.
- **What the E2E run covers.** `tests/e2e/interview-session.spec.ts`: Enrich →
  sheet → Start; the URL becomes the session's; round 1 (a suggestion taken
  where offered, picks by number key, text by Ctrl+Enter); the side panel's
  pending fields; round 2 with one question asked differently; round 3; the
  interview completes saying why; listed; a reload resumes it. A second spec
  starts from a kind's "Grill me" and stops, keeping the answer.
  `bible-a11y.spec.ts` runs axe on the setup sheet, a session with a round
  open, the stop dialog and the interviews list, and a keyboard-only walk
  (Enrich, Start, answer every question, finish the round), against the same
  server.

### The 2.3 seam

`src/lib/interview/setup.ts` is the only place the setup sheet meets the dials
API, and since the merge of 2.3 it reads and writes 2.3's routes:

- `loadSetupOptions` reads `GET /interview-packs` (the six personas, each with
  the mount gate's verdict) and the book's `GET …/interview-defaults` (the
  EFFECTIVE dials a session would start on, their `sources`, their `effects`).
  A persona whose pack does not mount is offered disabled with its refusal
  worded (`interview.setup.packRefusal.<MountRefusal>`), and is left out of
  the defaults the sheet opens on, so a stored default never starts an
  interview the server refuses. Up to three personas, in the order chosen;
  at the limit the unchosen boxes are disabled rather than an earlier pick
  silently dropped.
- The one-line previews are the server's `effects` while the sheet holds the
  defaults, and `dialEffects` (the same pure function the server ran) once a
  dial moves (`previewEffects`); depth shows rounds, detail the round cap,
  manner the calls a round. A dial still on a book or workspace default says
  so.
- `startRequestBody` sends `personaKeys` (at most three) and both toggles,
  which 2.3's strict `InterviewStartInput` requires (2.2's `persona` is now a
  400).
- `PACK_CHANGED` joined `StopReason` and the stop table; a PACK_CHANGED stop
  whose `stopDetail.problem` is `PACK_NOT_PINNED` (a 2.2 session) says to
  start a new interview. A 503 `PACKS_NOT_MOUNTABLE` names the packs its
  `details.packs` lists (a persona by name, a craft pack by its kind's label;
  a name the client does not know is left out, never shown raw), through
  `packOfName`.

## Decisions

- **Rephrase is its own prompt** (`interview.rephrase`, `question-rephrase.2.4.0`,
  fast tier per design 5.2, $0.05 per call) rather than a variant of the
  question prompt: 2.3's pack evaluation records are pinned to
  `QUESTION_PROMPT_VERSION`, so the question prompt's text and version are not
  touched. The old wording goes in a `previous-wording` DATA block (it was
  worded from the author's bible), never the system prompt. Code requires the
  same element, targets and mode, validates as for a round, and refuses a
  repeat of anything asked (the paraphrase thresholds) — falling back to the
  craft pack's example for a one-field FRONTIER question, else 409
  NO_REPHRASE with nothing written. The replacement and the original's
  `supersededAt` are one transaction; only one of the pair is ever answerable
  (`QUESTION_SUPERSEDED`), closing a round does not wait for a superseded
  question, and progress does not count it. A rephrase is shown in its
  original's place (`askedInOrder`), numbered after the round's last position
  in the table. Only an unanswered question is rephrased; at most
  `REPHRASES_PER_ROUND_MAX` (4) a round, and `SESSION_QUESTIONS_MAX` rose to
  80 to hold them (the session-bounds test).
- **The guard's flag is per question.** 2.2 counted flagged calls on the
  round; 2.4 carries the flag to every candidate of a flagged call
  (`Question.reviewRequired`) and the card shows it. A pack fallback is never
  flagged.
- **Autosave per answer.** A pick (click or number key) is saved at once; a
  written answer when saved (button, Ctrl/⌘+Enter, or Enter outside the box)
  or when focus leaves the box with it changed — never a debounced keystroke
  save, which would spend the 20-revision cap. One request per card at a
  time; a newer pick waits and goes next. A failed save keeps the answer,
  names the reason (the cap's refusal included) and offers Retry.
- **Keyboard.** Digits are bound with `within: cardRef` (WCAG 2.1.4: never a
  page-wide bare character), so they act only while focus is in the card and
  never in a text box (the hook skips editable targets). Enter saves what is
  unsaved and moves to the next question; a focused button keeps its own
  Enter. Ctrl/⌘+Enter saves from the text box and moves on. When a round
  arrives, focus goes to its first unanswered question; after the last,
  to Finish round.
- **Finishing a round goes straight on.** Close (skipping what is left, the
  author's act) then the next round's stream, unless the session ended.
- **The side panel writes nothing.** An answered field reads "Pending
  enrichment" with the answer, read-only; 2.5 turns answers into proposals.
- **Words, not codes.** Stop reasons and refusals are worded from their codes
  (`interview.stop`, `interview.errors`); an unknown code reads as the generic
  sentence. A 503 is "AI is not available here" whatever 2.1 named: the client
  does not spell 2.1's reason codes, one of which is a server variable's name
  (`scripts/check-build.js` refuses a client chunk naming one). A session that
  asked nothing reads "Not assessed" (rule 6).
- **The list names element sessions** (`SessionSummaryView.targetElementName`,
  read in one query), so the interviews page needs no second request.
- **READER.** No Enrich, no Grill me, no controls: questions and answers as
  text, and the list.

## Review (after the merge of 2.3)

What the review of `dd02238` and the 2.3 wiring changed, each with a test that
fails without it:

- **A close or a stop could overtake an answer and lose it.** A written answer
  was saved on blur, so "Skip the rest and finish" (or Enter on it right after
  Ctrl+Enter) sent the close while the save was in flight: the close skipped
  the question and the save was refused ROUND_NOT_OPEN; a stop did the same
  (INTERVIEW_NOT_ACTIVE); text never blurred was not sent at all. Now
  `QuestionCardHandle.flush()` saves what is on screen and waits for every
  save; finishing and stopping flush every card first, "skip the rest" is
  decided from what is still unanswered AFTER the saves, and a save that failed
  holds the round (the answer stays, with Retry). Text set aside by Skip or
  Decide later is never flushed over the author's choice. Leaving the page
  with an unsaved answer asks first (`beforeunload`).
- **The rephrase cap did not hold under concurrency.** It was counted only
  before the model call; two rephrases racing for a round's last one both
  wrote. It is counted again under the session lock before the write.
- **A rephrase could ask what the bible now answers (rule 5)**, when the
  author filled the field after the round opened. Refused 409
  ANSWERED_IN_BIBLE before any call, and checked again under the lock.
- **A rephrase was taught packs the session never pinned, or that do not mount
  (D11)**: it read the deployment's registry directly. It now asks the same
  `pinMismatch` a round asks (503 PACKS_NOT_MOUNTABLE, 409 PACK_CHANGED), and
  its prompt version names its packs (`packsVersionOf`), as a round's call's
  does (rule 9).
- **The stub's loopback rule lived only in the start-up check**, which is
  skipped for a process carrying `next build`'s phase marker. `stubModelActive`
  now asks `loopbackStubMode` in production itself.
- `InterviewsList`'s unused `canEdit` prop is gone; a guard holds every
  client-reachable module off `src/lib/ai/**` (the stub included); the SSE
  framing is tested against author text carrying blank lines and `data:` lines;
  and the flag is tested never to come from what the model wrote.



- The first `GET interview-packs` in a server process replays every pack's
  record (about four seconds of CPU on a cold server, blocking the event loop):
  2.3's verdict cache is per module instance, and the start-up warm-up runs in
  the instrumentation bundle, not the routes'. The setup sheet waits on it.
- A per-tenant stream capacity (inflect's `stream-capacity.ts`) is not carried:
  the round's GENERATING claim already allows one generation per session.
- A real-model evaluation record for the rephrase prompt (rule 9; the
  structural tests are `tests/unit/interview/rephrase.test.ts`).
