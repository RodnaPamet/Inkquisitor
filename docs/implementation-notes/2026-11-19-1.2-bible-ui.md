# 2026-11-19 — 1.2 Bible workspace UI

## Design

Three pages under `/w/[workspaceSlug]/books/`, each a server component that
reads through the 1.1 usecases with `getWorkspacePageCtx` and hands plain data
to one client component:

```
books/                              BooksList        EntityListPage, create in a Modal
books/[bookId]/                     BookBoard        DashboardLayout, one card per kind, create in a Modal
books/[bookId]/elements/[elementId] ElementPage      EntityDetailLayout: Fields | History tabs, Relations rail
```

- **Permissions come from the server.** Each page passes
  `canEdit = ctx.permissions.bible.edit`; no client code reads a role. A
  reader gets every value as text (a rich-text value through `htmlToLines`,
  a choice by its option label) and no edit, create, relate, restore or delete
  control — not disabled controls, which could still emit an edit.
- **Templates reach the browser as data.** `src/lib/bible/ui-model.ts` builds
  what a page needs from the registry — `kindSummaries()` (label and field
  count per kind), `fieldDefsFor(kind)`, `relationOptionsFor(kind)` — so the
  client bundle carries a few plain objects, not every template and the Zod
  schema that parses them. The client talks to the 1.1 routes through
  `src/lib/bible/api-client.ts` (a URL table and a `fetch` wrapper that throws
  `BibleApiError` with the API's `details.reason`); refusals are worded from
  the reason through `bible.errors`, never from the server's English.
- **Completeness** (`src/lib/bible/completeness.ts`) is filled template fields
  over template fields × entries. The empty denominators are states, not
  numbers: no entries is `not-started`, a template with no fields
  `not-assessed`; only a measured value draws a bar (a native `<progress>`),
  so nothing can read as 0% or 100% of nothing. The counts come from the list
  route: `listElements` now answers each element's `filledFieldCount`, the
  stored keys its kind's current template has (keys only: nothing is
  decrypted to count).
- **Autosave** (`src/components/bible/use-element-autosave.ts`). Edits queue
  by key; a 1 s debounce sends the element's own columns through `PATCH` and
  its fields through `PUT …/fields`, one request at a time (an edit made while
  one is in flight goes in the next). A failure puts the batch back beneath
  any newer edit, keeps the inputs as typed, shows "Not saved" with the
  reason and a Retry, and the next edit sends it again. Unmounting mid-debounce
  sends what is pending; a browser unload with unsaved changes asks first.
  `baseVersion()` holds the version number the last answer named, which is
  what 1.H's optimistic check will send; conflict handling is not built.
- **Field editors** follow the template's type: text → `<Input>`, rich text →
  `<RichTextEditor>` (HTML, loaded with `next/dynamic` so Tiptap stays off the
  other pages; its markdown mode is saved as escaped paragraphs, so the stored
  value is always HTML), choice → `<Combobox>`, scale → `<ToggleGroup>` over
  1..5 with the template's anchors, list → one `<Input>` per item. Each has a
  clear affordance; a cleared value is sent as `null`.
- **History.** Versions newest first with their source badge; `<VersionDiff>`
  over any two, fed with each snapshot rendered as labelled lines
  (`src/lib/bible/snapshot-text.ts`: template labels, option labels, scale
  positions, rich text as its text) rather than JSON. The list carries no
  snapshots, so the two compared versions are fetched when picked and cached;
  until both are in, the diff body is hidden. Restore first flushes pending
  edits (and refuses if that fails), calls the restore route, then re-reads
  the element and the history; the editors re-seed from the restored values.
- **Relations.** Two Comboboxes: a relation option (the kind's own types, the
  inverse of every type another kind declares towards it, `related to`), then
  an element of the book of a kind that option allows, never the element
  itself. An `incoming` option is stored from the other element, so its
  request names the other element as `from`. The API's `label` for each
  existing relation is already this end's (label or inverse label).
- **Destructive actions use the undo toast.** Deleting the element makes the
  page read-only at once and sends `DELETE` when the window closes, then
  opens the book; Undo gives the page back. Removing a relation hides its row
  and sends `DELETE` after the window.
- **Enrich** is `<Button disabledTooltip>`: focusable, `aria-disabled`, its
  reason ("Enrichment arrives with interviews") as tooltip and description.

## Decisions

- **No new route.** Everything the UI needs is a 1.1 route; the board's counts
  are one more member of the element list's answer, not a new endpoint.
- **"Not started" means no entries.** A kind with entries and nothing filled is
  a real 0 of a real denominator, so it is measured (0 of 14). Each entry on
  the board shows its own `filled/total`.
- **A `<progress>`, not a chart or a styled width.** It carries its value for
  assistive technology, and is painted through the tokens with pseudo-element
  variants; no inline width.
- **The debounce is 1 s.** Steady typing is one version, and a burst of edits
  stays well inside the mutation tier's 60 a minute (a 429 is an ordinary save
  error: the edit is kept and retried).
- **The page keeps what the author typed.** A save's answer updates the
  version, name and status shown in the header, never an input, so a slow
  answer cannot overwrite newer typing; what the sanitiser changed shows on the
  next load or after a restore.
- **Delete waits on the element page**, read-only, rather than leaving at
  once: the board is server-rendered, and leaving before the request would
  show the element still there for the length of the window.
- **`VersionDiff` fix.** Each side is trimmed, so a version's last line had no
  newline and `diffLines` showed it removed and added again whenever a line
  followed it in the other version; `ignoreNewlineAtEof` (jsdiff 9) fixes it.
- **Read-only rich text is plain text.** Rendering the stored HTML would need
  `dangerouslySetInnerHTML` on the client; its text is enough to read, and
  formatting is back in the editor.
