## Design

```
2.1 / 4.1 usecase ── runInWorkspaceContext(ctx, db => …)
   │  embed:  getEmbeddingProvider() → stub (dev/test) | TEI (inside the deployment)
   │  hash:   vectorContentHash(text)            HMAC under deriveSubkey(…)
   ▼
getVectorRepository().upsert(db, workspaceId, records)      validate (strict), metrics
   ▼
pgvector backend ── refuses unless the tx is app_user bound to that workspace
   ▼
"VectorEmbedding"  FORCE RLS · workspace_isolation · superuser_bypass
                   (workspaceId, revision, sourceModel, sourceId, chunk) unique
                   (workspaceId, bookId) → Book, ON DELETE CASCADE
                   CHECKs: dims = vector_dims, non-zero, hash, names
                   vector_embedding_delete_with_source('<Model>') for source tables
```

**One table, vectors only.** A row is a key, a nullable book scope, a keyed
content hash, the dimension count and the vector. The text stays in its source
row (a question, an element, a fact, an answer), encrypted under the
workspace's data key; a search returns references and scores, and the caller
reads the text back through the source's own repository under RLS. So a
vector is a derivative of an encrypted column (roadmap 4.H(4)): losing the
table loses nothing, `rebuildRevision` restores it, and it is deleted with its
source three ways — the usecase's `deleteSource` on the same transaction, the
`vector_embedding_delete_with_source()` trigger a source table attaches (for
deletes no usecase sees, such as a cascade), and the book's and workspace's
cascades.

**The caller's transaction.** Inflect's backend opens its own tenant
transaction per call. Inkquisitor's repositories take the `db` a usecase's
`runInWorkspaceContext` hands them, so the store does too: an upsert commits
with the change that caused it, and a source row and its vectors are deleted
atomically. To keep that from becoming a way around RLS, the pgvector backend
asks the transaction first and refuses `NOT_IN_WORKSPACE_CONTEXT` unless it is
`app_user` with `app.workspace_id` equal to the workspace the call names. A
rebuild (many transactions) takes an `inWorkspace` opener instead.

**Exact search, no HNSW index yet.** An HNSW index on an untyped `vector` is
an expression index on one dimension cast, and the production model — so the
dimension — is chosen when 2.1 first embeds author text. Until then a search
is an exact scan of one workspace's rows of one revision (optionally one
book's), through workspace-leading btrees: recall 1, and none of the
shared-index post-filtering that made inflect's backend three strategies
deep. Past `EXACT_SCAN_WARN_ROWS` (20,000) a search logs
`vector_store.search_large_exact_scan`: the signal to add the partial index
and port inflect's iterative-scan search for that revision.

**The embedding seam.** `getEmbeddingProvider()` returns the deterministic
feature-hashing stub in development and test (the default when
`EMBEDDING_PROVIDER` is unset) and self-hosted Text Embeddings Inference in
production. TEI is the production provider so that author text reaches no new
sub-processor: its base URL must resolve only to addresses inside the
deployment (loopback, RFC 1918, unique-local), checked structurally when the
route is chosen and on every resolved address at dial time, pinned, with a
deadline, a byte cap and no redirects (`src/lib/ai/in-deployment-service.ts`,
carved whole). There is no external embedding route; adding one is an owner
decision, not a variable. Production refuses the stub at start-up, refuses a
TEI route that is incomplete or outside the deployment, and starts with no
provider when `EMBEDDING_PROVIDER` is unset (nothing embeds before 2.1, which
makes `tei` required).

**The embedding revision names the vector space**:
`<model>:d<dimensions>:p<8 hex of the prompt prefixes>`. The store never
compares two revisions, which is what lets the stub be a default here when
inflect never selects it: a stub vector lives in `stub-feature-hash@1:d64:…`
and can never be found by, or mistaken for, a real model's.

**The image.** `deploy/postgres/Dockerfile` and `smoke.sh` are inflect's,
instruction for instruction: `postgres:16-alpine` by tag (same musl and
collation as the image the dev stack ran before), gosu rebuilt from source
with a pinned Go (the upstream binary's Go standard library carried fixable
CRITICAL/HIGH findings), pgvector v0.8.7 by tag and commit, built for generic
x86-64, toolchain removed in the layer. `.github/workflows/postgres-image.yml`
publishes it: `decide` (weekly, or when the upstream digest moved, or on
dispatch; main only), then BUILD → SMOKE → Trivy (blocking) → PUSH of the
scanned bytes, the immutable per-build tag before the moving line tag.

**CI before anything is published.** Test and E2E build the Dockerfile in the
job (buildx with the GHA cache, scope `inkquisitor-postgres`) and run it with
`deploy/postgres/start.sh` in place of the `postgres:16` service container,
which lacks pgvector. Nothing is pulled from GHCR, so CI is green before the
first publish, and a pull request that changes the Dockerfile tests the
Dockerfile it carries. The Docker job builds it once more uncached on a fresh
base, smoke-tests it and gates it with the same Trivy rule as the application
image — inflect's separate `Postgres image` job folded into an existing job,
so the eight check names are unchanged.

## Decisions

- **Vectors only, no chunk text.** Inflect stores chunk text (encrypted) in a
  `KnowledgeChunk` table because its sources are long documents cut into
  passages that a RAG answer quotes. Inkquisitor's first two callers embed
  rows that already hold their text (a question; an element, fact or answer),
  so a chunk table would be a second encrypted copy of author text with its
  own key rotation and deletion to get right, for nothing a source read does
  not give. `chunkIndex` stays in the key for a source long enough to cut; a
  caller that cuts recomputes the chunk from the source with its own versioned
  chunker. If a later phase needs passage text it cannot recompute, it adds an
  encrypted chunk table then.
- **Keyed content hash, not plain SHA-256.** Much author text is short (a
  one-word answer, an eye colour), and a plain digest of a short text is
  recovered by hashing guesses. HMAC-SHA256 under a purpose-labelled subkey of
  the master key material is as stable for idempotence. Master-key rotation,
  when it arrives, must keep the subkey's derivation (inflect's
  `DERIVED_SUBKEY_KEY`) or every vector looks stale and is re-embedded.
- **The vector itself is a plaintext derivative.** An index needs plaintext
  floats, and an embedding leaks something of its text. It is classified as
  author text: it lives only in this database and its backups, never in a log,
  a metric label or a job payload, and is deleted with its source.
- **A book scope, not a generic one.** Every caller the roadmap names embeds
  something of one book, and a real composite foreign key to `Book` gives the
  database's own guarantees (no vector under another workspace's book; the
  book's deletion takes its vectors) that a free-form scope string cannot.
  Workspace-level sources pass `bookId: null`, and the record must say so.
- **A trigger function, attached by each source table.** A polymorphic source
  cannot have a foreign key. The function takes the model name as its one
  argument (not `TG_TABLE_NAME`, which `@@map` could make differ) and runs as
  the deleting role, so under `app_user` RLS confines it to the deleted row's
  workspace. A trigger attached without the argument refuses the delete.
- **Always pgvector, no switch.** Inflect's `VECTOR_STORE_BACKEND` exists
  because its store is optional. Here the migration creates the extension, so
  no deployment lacks it; one variable fewer.
- **Stub by default outside production.** The task's default; made safe by
  the revision (stub vectors are their own space) and by the start-up check.
- **No reranker, no residency routing.** Both are compliance-RAG machinery
  with no caller in the roadmap.
- **`undici` is a dependency.** The in-deployment dial pins the connection to
  the checked addresses with an undici `Agent`; Node's bundled fetch cannot
  take one from outside. Carried at inflect's range.
- **The image job is folded into Docker.** A new `Postgres image` check would
  be a new required-check name to configure; the Docker job already scans
  images, and its tests now pin both gates.
- **A revision's first write is serialised.** Writes take the (workspace,
  revision) lock SHARED, so two first writes of a revision could each see no
  rows and commit vectors of two dimension counts, after which every search,
  upsert and rebuild of that revision refused `REVISION_DIMENSION_MISMATCH`.
  A write that finds no rows takes a second, exclusive first-write lock (held
  to commit) and reads the count again; under READ COMMITTED, which
  `runInWorkspaceContext` uses, the loser then sees the winner's rows and is
  refused by name. Only first writes pay for it.
- **Components are judged as 32-bit floats.** pgvector stores `real`, so the
  repository rounds each component with `Math.fround` before judging it: a
  double past the float range (which pgvector refuses with a raw 22003 that
  quotes the value) and a vector that is zero once rounded (the CHECK's 23514,
  or a NaN cosine as a query) are `INVALID_RECORD` / `INVALID_QUERY`, the same
  in both backends.
- **CI waits for the real server.** The upstream entrypoint does initdb's
  work on a temporary server listening on the Unix socket only, so
  `start.sh` and `smoke.sh` ask `pg_isready` over TCP, which only the real
  server answers; a socket probe could pass against the temporary one.
- **Package write belongs to the pushing job.** The publish workflow grants
  `contents: read`; only `build-scan-push` adds `packages: write`.
- **Local verification.** The sandbox's Docker daemon could not pull from
  Docker Hub (rate-limited) or reach Alpine's package mirror, so the image was
  not built here; pgvector v0.8.7 (the pinned commit, same flags) was compiled
  against the local PostgreSQL 16 and the suites ran on a cluster of their
  own. CI's Docker job is the first build of this Dockerfile under this name.
