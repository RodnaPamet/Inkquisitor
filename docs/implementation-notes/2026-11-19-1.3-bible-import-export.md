# 2026-11-19 — 1.3 Bible import and export

## Design

Four routes under `/api/w/[workspaceSlug]/books/[bookId]/`, two usecase
modules, and the format between them:

```
GET  export/bundle         bible.view   exportBibleBundle  → readBibleBundle → bundleFiles → writeZip
GET  export/pdf            bible.view   exportBiblePdf     → readBibleBundle → renderBiblePdf (lifted pdfkit helpers)
POST import/bundle         bible.edit   importBibleBundle  → scan → readZip → parse + validate → one transaction
POST import/concept-note   bible.edit   importConceptNote  → scan → sanitise → a RESEARCH element
```

### The Markdown bundle (format version 1)

```
manifest.json            {"format":"inkquisitor-bible","version":1}
book.md                  frontmatter: title, logline, genre, audience, targetLength, stage; a contents list
<kind>/_index.md         per kind with entries: the entries, linked (for reading; not imported)
<kind>/<slug>.md         per element: YAML frontmatter + a Markdown body
```

`<kind>` is the kind in lower case (the template file's name). The index is
`_index.md` because no slug can start with `_`.

An element file's frontmatter, in a fixed key order: `kind`, `name`, `slug`,
`status`, `customLabel` (CUSTOM only), `summary`, `fields` (filled fields by
template key, in template order: text and rich text as strings, a list as a
sequence, a choice as its option VALUE, a scale as its number) and
`relations` (the relations STORED from this element: `type`, `to` as the
target's slug, `note`). Absent means empty; nothing is written as `null`.

The FRONTMATTER IS THE DATA; the body (the name, status, summary, each filled
field under its template label, relations read from both ends) is generated
from it for a person to read, and an import never reads it.

### Determinism

Every file is a function of the stored bible: elements in kind order then
slug, fields in template order, relations by type, target and note, fixed key
order, no timestamps or ids, YAML written with fixed options (`lineWidth: 0`,
literal block scalars, no anchors). The zip (fflate) has entries in name
order, DEFLATE level 6, no directory entries or extra fields, and every entry
dated 2000-01-01 00:00 — built from local-time components, because fflate
writes the DOS date from the local getters, so the bytes do not move with the
server's timezone (a unit test zips under two far-apart zones). Exporting an
unchanged bible twice gives the same file, and the round trip (export, import
into an empty book with its details applied, export) gives the same bytes.

### Import

Every upload, before anything is written:

1. **Bounded.** The bundle route reads at most 20 MiB of body
   (`readBoundedBytes`, the bounded reader `readJsonBody` now shares: 413
   `BODY_TOO_LARGE` on the declared length, or as soon as the streamed bytes
   pass it); a concept note comes through `readJsonBody`'s 2 MiB.
2. **Virus-scanned.** The upload's bytes through `scanBuffer`. INFECTED is
   always refused (`UPLOAD_INFECTED`); a scan that could not run is refused in
   `strict` mode (503 `SCAN_UNAVAILABLE`) and let through with a warning in
   `permissive` / `disabled` — the download policy (`isDownloadAllowed`)
   applied to an upload. Without clamd, development and the integration
   suite (strict by default) refuse; the E2E server runs `disabled`. Tests
   inject a scanner (`ImportDeps.scan`).
3. **Unpacked within bounds** (`readZip`, our own reader over `node:zlib`):
   entry count (on the directory's own count, before reading one), each
   entry's and the total declared size, the compression ratio (past 64 KiB),
   unsafe names (absolute, drive letter, backslash, `.`/`..`/empty segment,
   control character), duplicates, encryption, unknown methods, ZIP64 and
   split archives — all before inflating. Each entry is then inflated with
   `maxOutputLength` at its declared size and its length and CRC-32 checked,
   so an entry that lies about its size stops at the claim.
4. **Parsed safely.** UTF-8 only (a BOM and CRLF tolerated); YAML 1.2 core
   schema with any alias, any explicit tag, a duplicate key, an error or a
   warning refused by name; every object strict.
5. **Validated and sanitised through the 1.1 paths**: `requiredLine` /
   `optionalBlock` / `customLabelFor` for the columns, `normaliseFieldEntries`
   for the fields. An unknown kind, field key, choice option or relation type
   is refused with a named reason, never dropped.

Every problem is collected (up to 100) and answered as one 400
`BUNDLE_REFUSED` with `problems: [{ path, reason, key? }]`.

## Decisions

- **One transaction per bundle.** The brief preferred atomic; a refusal
  writes nothing, and a database failure part-way rolls everything back, so
  an author never has half a bundle to reconcile. Imports into one book are
  serialised by an advisory lock (`bible-import:<bookId>`); the transaction
  may run 120 s. The cost is that one bad file holds back the rest, which the
  report makes cheap to fix: every problem is listed at once.
- **The file is the element's whole state.** A field the file leaves out is
  cleared on re-import, so editing a bundle and importing it again does what
  the file says. Elements the bundle does not name are left alone, and no
  relation is removed: an import merges, it never deletes.
- **Idempotence comes from the versioned save.** Every element goes through
  `bible-common`'s lock → change → `recordVersion` with source `IMPORT`, and a
  save that changes nothing writes no version, so a second import of the same
  bundle writes nothing at all; a changed element writes exactly one version.
  An element of the same slug but another kind is refused `KIND_CONFLICT`
  (kinds are fixed).
- **Relations are resolved by slug after the elements**, against the bundle
  and the book, from the element whose file lists them (it must be the kind
  that declares the type, as a manual relation must). A symmetric relation
  is found in either direction. An existing relation's note is brought to the
  file's (`BibleRelationRepository.updateNote`, classified in the sanitiser
  guard); relations are not versioned, as in 1.1.
- **Book details only on request** (`?bookDetails=apply`, a checkbox in the
  modal). Importing into a book with its own title never renames it by
  surprise; the round trip into an empty book applies them, which is what
  makes `book.md` identical.
- **Rich text stays HTML in the frontmatter.** Converting to Markdown is lossy
  both ways; the stored value is already sanitised, and the sanitisers are
  idempotent on their own output, so re-importing an export re-sanitises to
  the same string. The readable body reduces rich text to its text; text that
  spells a tag is dropped from the body (never written as markup into a
  Markdown file) and kept exactly in the frontmatter.
- **Export only what an import accepts.** A stored value under a key the
  kind's current template no longer has stays in the element's history, not
  in the export. Export and import share one bound (2,000 elements, 20,000
  relations); a book past it is refused `EXPORT_TOO_LARGE` (each read asks
  for one more than the bound) rather than exported in part.
- **An empty bundle is refused** (`BUNDLE_EMPTY`): an import that read no
  element would otherwise answer success having done nothing (rule 6).
- **Nothing uploaded is stored as a file.** The bytes are checked and applied
  in memory. Writing the bundle to object storage would put author text at
  rest unencrypted (storage does not seal), against rule 4; only the
  resulting rows remain, encrypted as every bible row is. Exports are built
  per request and never stored either.
- **The upload body is the zip itself**, not multipart: one bounded read, no
  multipart parser. A concept-note file is read as text in the browser and
  sent as JSON, so it shares the JSON body's bound and the same scan.
- **Our own zip reader.** fflate writes; reading is ours because fflate's
  `unzipSync` trusts the declared size (it allocates it, and inflates a
  lying entry to the end of its data) and checks no CRC. `node:zlib`'s
  `maxOutputLength` stops a lying entry at its claim. jszip (which inflect
  carries) was passed over for the same reason and for its size; fflate is
  MIT and maintained. Neither fflate nor `yaml` (ISC) nor `pdfkit` (MIT) is
  ported code, so `NOTICE` is unchanged; they are dependencies.
- **The concept note's field.** RESEARCH had no field for free text, so its
  template gains `notes` (rich text, optional, last), worded after CUSTOM's
  own Notes field. The note's text becomes paragraphs (`<p>`, a `<br />` per
  line), sanitised as any rich-text value; the name is given or the first
  line (cut at a word to 120 characters). It is idempotent per slug as a
  bundle element is: the same note twice changes nothing, a changed note
  under the same slug writes one version, and a slug another kind holds is
  `KIND_CONFLICT`. Adding a template field is a content change; it is flagged
  for the owner.
- **PDF fonts.** PDFKit's standard Helvetica, as inflect uses: `pdfkit` is a
  server external package so its `.afm` metrics load from node_modules at run
  time (the worker bundle keeps every package external already). The standard
  fonts carry WinAnsi only, so text is folded through `toWinAnsi` and anything
  else prints as `?` rather than as a wrong letter; embedding a Unicode font
  is a follow-up. The PDF's colours are the light theme's tokens, held equal
  to `tokens.css` by a test.
- **Audit.** `BIBLE_EXPORTED` (format, counts), `BIBLE_BUNDLE_IMPORTED`
  (counts, bytes, whether book details were applied) and
  `BIBLE_CONCEPT_NOTE_IMPORTED` (outcome, version, length), each in the
  transaction that did the work; never a name or any text.
- **No help page.** `docs/user/` has no bible page yet, so the format is
  documented here and in the module header; the site manifest is unchanged.
