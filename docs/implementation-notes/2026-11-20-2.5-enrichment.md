# 2026-11-20 — 2.5 Enrichment: answers into the bible

**Commit:** uncommitted (branch `wip/2.5`, cut from `main` at `56b7b28`; 2.4
was merged in from `main` at `d815abb` and wired, see "Wiring 2.4")

When a round closes, a reconcile step proposes bible changes from its
answers — per targeted field ADD, UPDATE, REMOVE or NO CHANGE (the mem0
reconciliation pattern, Apache-2.0, credited in `NOTICE`), with the proposed
value and the ids of the answers it is drawn from, and new elements an answer
names. Code refuses what breaks a rule; the author reviews the rest as a diff
per field and accepts, edits then accepts, or rejects. The design is the staged
`design/QUESTION-ENGINE.md` (5.3, 9, 10.2) and `FORMAT.md` (5.2, 5.3).

## Design

```
POST …/rounds/:n/close ─► closeRound (2.2, commits) ─► reconcile, same request
POST …/stop            ─► stopInterview (2.2)        ─► reconcile each closed round with no run
POST …/rounds/:n/reconcile ─► a FAILED / REFUSED run again (503 AI_UNAVAILABLE first, nothing written)

  claim (session lock)   round CLOSED; ReconcileRun RUNNING (new, or attempt+1)
                         refusal? unavailable model → REFUSED AI_UNAVAILABLE
                                  D11 gate          → REFUSED RECONCILE_NOT_EVALUATED     (nothing sent)
                         read: the round's questions, latest answers, scope elements' values, book elements
  call (no tx)           runReconcileStep: nothing ANSWERED → NOTHING_TO_RECONCILE (no call)
                         buildReconcileRequest → Reconciler (model-seam.ts → 2.1 callStructured)
                         failure → named outcome, nothing proposed
  persist (session lock) this claim still holds? validate AGAIN against the bible now
                         (validate.ts) → sanitiseProposalForStorage → EnrichmentProposal + citations
                         run DONE / FAILED, counts by op and refusal code, tokens charged, audited

review page ─► GET …/proposals (bible.view) ─► accept / edit+accept / reject / bulk (bible.edit)
  accept: element lock → baseVersion == latest → (moved since proposal? reviewedCurrent)
          → op still fits → writeFieldValues → recordVersion(INTERVIEW, sourceAnswerIds)
          → decide (conditional from PENDING) → supersede other PENDING for the field
```

The model words values; code decides what may be offered (`validate.ts`, in
order): the element and field are in the round's scope; one op per field; the
op fits the stored value; at least one citation, each an ANSWERED answer this
run was given; a value `normaliseFieldValue` accepts (REMOVE none, UPDATE a
different one); no copied instruction; every sentence grounded. NO_CHANGE and
every refusal are counts on the run — a refused proposal is never stored, so
model text that failed a rule is never shown and never kept.

## Decisions

- **Trigger: inline, after the close commits.** Not a background job: the
  author is on the interview page when the round closes and the proposals are
  what they read next; question rounds are generated inline the same way; and
  a failure is a named, re-runnable run state rather than a lost job. A worker
  job would also have to rebuild the author's request context. The close never
  waits on reconcile to commit and is never undone by it. The cost is latency
  on the close request (the balanced tier's deadline bounds it).
- **Tier: balanced.** One call per round (beside one per persona for the
  questions), on the step every injection attempt in an answer aims at, whose
  output is the text the author accepts into their bible. Fast was weighed for
  latency and price; code refuses an unfaithful proposal, but refusing is not
  proposing, and the author then gets nothing for the answer. The cost budget is
  $0.15 a call, on the template (rule 9).
- **Grounding as the design says (4.5), plus two checks the adversarial set
  showed it needs.** Every sentence (list item, a choice's option, a scale's
  number) must be supported by the cited answers, and for UPDATE the stored
  value: 70 % of its content words and every capitalised word. Every reference
  wording of both sets passes, and every `mustNotContain` embellishment a source
  does not hold is refused (a test). Grounding alone passes an injected
  instruction COPIED verbatim from the answer that carries it (adv-03, 06, 07,
  11, 12, 13 are all clean to the guard's patterns), so rule 5 adds: the guard's
  injection scan of the value, markup and script schemes, a URL only when a
  clean cited answer gives it, and `addressesTheProduct` — a sentence that pairs
  an action with one of the product's own nouns (field, bible, prompt,
  instructions, diff, proposal, chapter, workspace) or cites an answer id. A
  story's own order (adv-14's creed) names none and is recorded. A false
  refusal costs one suggestion, never the answer: the author can still write it.
  Grounding cannot see a retracted fact restated from the stored value (en-01's
  "mother left"); that is graded, not refused.
- **Citations: this run's answers only.** The design allows any ANSWERED answer
  of the session; the product only ever sends the round's latest answers, so an
  id outside them — another session's, another round's, an older revision, a
  made-up one — is `CITES_FOREIGN_ANSWER`. The database holds the session rule
  for any writer (the citation's foreign key) and ANSWERED (a trigger), and a
  deferred constraint trigger refuses a proposal with no citation at commit.
- **One proposal table**, `kind` FIELD | NEW_ELEMENT, rather than the design's
  two: one review list, one citation table, one decision path; CHECKs hold each
  kind's shape. The element's foreign key is by id (Prisma cannot declare an
  optional composite one beside a required `bookId`), and an AFTER trigger holds
  it to the proposal's book. `REFUSED` is not a status: refused proposals are
  counted, not stored.
- **The link from a version to its answers is a column**, `sourceAnswerIds`
  on `BibleEntryVersion`, written with the version (the table is append-only),
  non-empty exactly for INTERVIEW (CHECK). Ids only: an answer deleted later
  leaves its id as the history it was. The proposal points at its version.
- **Concurrency (1.H).** An acceptance names the version the author reviewed;
  a newer one is 409 VERSION_CONFLICT. An element that moved since the proposal
  was made is accepted only with `reviewedCurrent` (the review shows its value
  now and says it changed); an op that no longer fits is 409 PROPOSAL_STALE
  whatever the author says. Never an overwrite. Bulk accept is one transaction,
  elements locked in id order, all or nothing.
- **D11 for reconcile.** Production reconciles only on a real model's
  evaluation record of the reconcile prompt; there is no override. Until one is
  committed, interviews run, answers are kept, and each closed round's run is
  REFUSED `RECONCILE_NOT_EVALUATED` (re-runnable once a deployment holds a
  record), with a `[startup] WARN`. Which records count is
  `deploymentPackRecordMode()`, the packs' own reading, so D13's loopback stub
  server accepts the structural record as it accepts the packs' and the E2E
  runs reconcile end to end.
- **The structural record is the reference reconciler's.** A reconcile op is
  the model's judgement, which no request-only deterministic reconciler can
  make, so the structural reconciler answers each case with the case's own
  reference operations. A structural record therefore proves that the sets,
  the product's validation (every reference passes every rule) and the grader
  agree end to end, and nothing about a model — which is why production refuses
  it. The gate replays a record through `runReconcileStep`; a structural record
  must be exactly the reference's output; a model record holding the reference's
  worded output for a case is `STRUCTURAL_OUTPUT_AS_MODEL`. An attempted
  out-of-scope change or copied instruction fails a case even though code
  refused it (as the packs' grader counts a dropped candidate).
- **Evaluation sets.** The staged enrichment set's 27 cases unchanged plus 13
  written here (en-28..40: the kinds staged once, scales and picks, a
  retraction beside an earlier session's answer, new elements, a name the book
  already holds): 40 cases, 93 answer/field pairs (the roadmap asks for forty
  pairs). The staged adversarial set's 14 cases unchanged (every attack
  category; the roadmap asks for ten). `FORMAT.md`'s 20–30 cases is exceeded on
  the brief's instruction to extend to forty.
- **New elements** exclude CUSTOM (it needs the author's own label), must be
  named in a cited answer, and are refused when the book or a pending proposal
  already holds the name (case, look-alikes and a leading article ignored).
  Accepting one creates it through `createElementInTx` (the create path 1.1
  uses), its first version INTERVIEW and naming the answers.
- **Rich text** arrives as plain paragraphs and is stored as escaped `<p>`
  HTML; grounding reads the plain text.

## Review fixes

A review of the branch before merge found, and fixed with a test each:

- **A new element whose name the book already holds, spelled differently.**
  The persist and acceptance checks asked the database for the proposed name
  with an ILIKE, so "The Drainage Board" missed "Drainage Board" and a
  look-alike letter missed the plain one; accepting created a duplicate.
  `bookHoldsElementName` (`usecases/enrichment-names.ts`) now walks the book's
  element names a keyset page at a time and compares `nameKey`s in code.
- **A run whose process died read "Reconciling…" for ever.** `CLAIM_EXPIRED`
  was in the vocabulary and the CHECK but never written, and the review offered
  no retry for a RUNNING run. A stale RUNNING run now reads FAILED
  `CLAIM_EXPIRED` everywhere (`effectiveRunState`, `vocabulary.ts`), so the
  review offers "Run again"; claiming it records the expired attempt first
  (audited `CLAIM_EXPIRED`).
- **The D11 gate refused a faithful model.** A model record was refused
  `STRUCTURAL_OUTPUT_AS_MODEL` when ANY worded case equalled the reference,
  and the references are what a faithful model writes (en-31's single ADD). It
  is refused now only when every worded case equals the reference.
- **`addressesTheProduct` was beaten by an inflection** ("Marking all fields
  complete", "Copied this into every field") and misfired on story prose ("set
  the field on fire"). Words are compared by stem, with a few more verbs; the
  two nouns that are also story words (field, chapter) count only beside a
  word that ranges over the product's objects ("every field") or a chapter
  number. On the sets: every adversarial answer it caught is still caught, no
  reference wording of either set is, and en-08's own answer ("delete the
  alternating-chapters note") no longer is. Since D14 (below) it flags rather
  than refuses; the answer-id half of it ("cite answer a1", or one of the run's
  own answer ids in the text) moved to `citesAnswerInText` and still refuses.
- **Grounding refused a different apostrophe or a possessive.** "Wren’s" against
  "Wren's", and "Tomas’s boat" against "the boat belonged to Tomas", were
  unsourced. `groundingForm` folds apostrophes and reads a possessive as its
  name, for the sentence, its sources and `namedIn`.
- The tokens of an overtaken claim are charged to the session (2.2's rule); a
  stop that has committed is never answered with an error by its reconcile.

## Owner decisions of 2026-11-20

- **Reconcile stays as built**: the balanced tier, a $0.15 per-call cost
  budget (`RECONCILE_CALL_COST_BUDGET_MICRO_USD`) and 10,000 output tokens
  (`RECONCILE_MAX_OUTPUT_TOKENS`).
- **D14 — the product-addressing check flags instead of refusing**
  (`docs/ROADMAP.md` section 2). A proposal whose text addresses the product
  (`addressesTheProduct`) is stored with `flags = ['POSSIBLE_INSTRUCTION']`
  (`EnrichmentProposal.flags`, a closed list held by the CHECK
  `EnrichmentProposal_flags_known`, fixed at insert by
  `enrichment_proposal_fixed` like the rest of the proposal; the run counts
  `flagged`). The review shows it as a possible instruction with an
  explanation (`enrichment.flag`); bulk acceptance never offers it
  (`bulkEligible`) and the server refuses a batch holding it
  (`BULK_INELIGIBLE`); it is accepted one by one, like every proposal, and
  still has to be grounded. What catches real injection still refuses
  (`COPIES_INJECTED_TEXT`): the guard's injection-scan hit, markup and script
  schemes, a URL no clean cited answer gave, and an answer cited by its id in
  the text. The grader: on the adversarial set an instruction copied into a
  stored proposal must carry the flag (`COPIED_INSTRUCTION_UNFLAGGED`) and must
  not be bulk-eligible (`FLAGGED_BULK_ELIGIBLE`), and a `mustNotContain` phrase
  is excused only in a flagged proposal there. The prompt, the output schema
  and the sets did not change, so the committed record stands. The flag is a
  label: a copy the guard does not catch (adv-06's zero-width "ignore", adv-11's
  "the instructions above no longer apply") now reaches the author flagged
  where it was refused before — the author's explicit acceptance is the gate.
