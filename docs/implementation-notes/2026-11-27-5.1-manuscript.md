## Design

```
outline       Manuscript (one per book, made on first write) → ManuscriptPart → ManuscriptChapter → ManuscriptScene
              each level ordered by a fractional rank (story-order.ts: rankBetween / placeRank), unique per parent;
              a manuscript with one untitled part shows as chapters only (singleDefaultPart)
scene         title, text (TipTap HTML, prose profile), story time (free text), note — all encrypted, all sanitised;
              POV (a CHARACTER) and setting (a SETTING) by (bookId, elementId), ON DELETE SET NULL (col), kind held by trigger;
              wordCount (Intl.Segmenter), revision (the concurrency counter, distinct from versions)
links         SceneElementLink (mentioned | explicit, either or both); SceneBeatLink (a PLOT_BEAT, held by trigger) — both
              same-book composite foreign keys; mention links re-derived from the stored text on every text save
versions      SceneVersion / SceneNoteVersion: book-keyed (a scene's history outlives the scene, as an element's does),
              append-only by trigger, encrypted; source EDIT | RESTORE | IMPORT; note versions name RESEARCH proposals
text writer   manuscript-text.ts ONLY (D3): writeSceneText / checkpointSceneText / restoreSceneText / createImportedScenes
              version due ⇔ text differs from the newest version AND (checkpoint | newest older than 30 min by dbNow | none)
autosave      use-scene-autosave: debounced PUT …/text { html, baseRevision, checkpoint? }, one in flight; 409 → held,
              Reload theirs / Keep mine; idle 2 min → checkpoint; hidden / unload / unmount → keepalive POST …/checkpoint
import        POST …/import/preview (bytes) → 4.0's reader (parseSource: DOCX through mammoth's bounded worker, Markdown)
              → outline + proposed plan + HMAC token (fileSha256, 1 h); POST …/import (bytes again + x-import-plan) →
              token and hash checked → splitManuscript → ONE transaction, appended after what the manuscript holds
research FIT  a brief scoped to ≤ 8 chapters (or ≤ 12 scenes); FIT is shown ≤ 24 scenes as fenced `scene.N` blocks
              (title, chapter, POV, setting, story time, 600-character excerpt); a SCENE_NOTE proposal cites findings,
              is grounded in them alone, never prose; accepting appends to the scene's NOTE (a RESEARCH note version)
beat scenes   GET …/elements/:id/scenes — the beat's element page and the plot board's ElementSheet list them read-only
board cards   the plot board's map view carries `beatScenes` (manuscript-board.ts: per beat, the exact count and the first
              BOARD_SCENES_PER_BEAT in manuscript order) → SceneCardLayer, tldraw's `Overlays` (page space, above the
              shapes), cards across the bottom edge of the beat's card; never a record, a row or a save
```

LOCK ORDER (D25, extended): every bible lock → the manuscript's structure lock
(`manuscript:<bookId>`) → a scene's lock (`manuscript-scene:<sceneId>`) → the
elements a save names, `FOR KEY SHARE` (`lockElements`) → the scene's own row,
`FOR NO KEY UPDATE` (`lockSceneRow`) → link rows. Element rows before scene rows
is the order a bible deletion's cascade takes them (the element, then its links
and the scenes' POV / setting columns); the scene row before its links is the
order a part or chapter deletion's cascade takes them. So a save and either
deletion never wait on each other in a cycle. Audit rows are written last.

## Decisions

- **The revision is not the version.** Autosave moves `revision` on every
  changed save (and refuses a stale `baseRevision`); versions are history,
  written on a pause, on leaving and past the server's bound (D33). Folding the
  two together would either write a version every few seconds or let two tabs
  overwrite each other between versions.
- **A checkpoint carries no text.** The leave path sends only
  `{ revision }` with `keepalive`; the server versions the stored text when it
  is that revision. A tab closing mid-save therefore never writes a version of
  text the server did not accept, and the request body stays tiny for
  `keepalive`'s limit.
- **Links follow the text.** Mention spans carry only an element id; every text
  save re-derives the mention links from the stored HTML (ids of another book,
  or of nothing, are dropped by the sanitiser's check). Explicit links are the
  author's own and survive the text. Past `MENTION_LINKS_MAX` the mention stays
  in the text unlinked and the save says how many (`mentionsCut`).
- **The import re-sends the file.** Nothing is stored between preview and
  confirm: the preview's token binds the file's SHA-256 and the time, and the
  confirm reads the bytes again, so a different file is IMPORT_FILE_CHANGED and
  an old preview IMPORT_PREVIEW_EXPIRED. The file never enters the source
  library (D33). The confirm is one transaction whose statement count does not
  grow with the scenes within a batch of 500 (the 150,000-word test).
- **The kind checks are AFTER triggers.** A BEFORE trigger reads the element
  through row-level security, so a row of another workspace was refused as the
  wrong kind instead of by RLS (the RLS coverage suite caught it); as AFTER
  triggers RLS's WITH CHECK refuses it first, and an exception still undoes the
  statement.
- **Story time is free text,** as the bible's `story_time` is; ordering scenes
  in story time is a later subphase's.
- **A spent rank gap rebalances its parent** (`placeAmong`, review fix): about
  three hundred inserts at one spot, or a scene swapped up and down past its
  neighbour that often, spend a gap, which a long-lived manuscript reaches. The
  parent's rows take `rebalancedRanks` in the same order, in TWO passes (each
  row first to a temporary rank clear of every old and new one, then to its
  final rank), because the unique `(parent, rank)` is checked row by row inside
  one statement and a single pass could land a row on a rank another still
  holds. No version is written and no revision moves (a rebalance changes keys,
  not the book); one `MANUSCRIPT_ORDER_REBALANCED` audit row follows the row
  writes. Only a rank still past the bound is 409 `ORDER_RANK_EXHAUSTED`.
  Imports place with fresh evenly spaced ranks.
- **A research note never touches the text.** SCENE_NOTE acceptance appends to
  the note through `manuscript-notes.ts`, which does not import the text writer
  (the guard checks it); the note's version names the proposal and its
  findings, mirroring the bible's RESEARCH versions.
- **5.3's outbox has room.** A draft-fact extraction can hang off a trigger on
  `SceneVersion` inserts, as 4.1's outbox hangs off `BibleEntryVersion`, with no
  change to these tables.

## Review (2026-11-27): the owner's three decisions and the fixes

The owner's answers to the review are D33's addendum:

- **(A) Search and export land in 5.H.** Word search over scenes and the
  manuscript in the export; 5.H's text now names word search over scenes beside
  item 4's export. Recorded only.
- **(B) Scene cards on the plot board.** The scenes a beat links are drawn ON
  the board as read-only cards, and are display data only. The map view (every
  view: page load, refresh, save, restore) carries `beatScenes`, read by
  `manuscript-board.ts` in a constant number of statements (an aggregate count
  per beat, the bounded links, their scenes, chapters and parts), so each beat's
  total is exact and the cards are the first `BOARD_SCENES_PER_BEAT` (2) in
  manuscript order. `SceneCardLayer` draws them through tldraw's `Overlays`
  component — page space, ABOVE the shapes — because the derived layout leaves
  no free room beside or under a beat (a 16 px gap between beats, 16 px each
  side of a lane): the cards straddle the bottom edge of the beat's card, inside
  its width, so they never cover another beat and the layout is untouched. 3.3's
  ghosts are drawn by `OnTheCanvas`, which is UNDER the shapes; a card there
  would be hidden by the beat it belongs to. They are links (a plain click
  routes in the app, a modified click is the browser's), focusable, their
  pointer events kept from tldraw, behind their own error boundary; "+N more"
  opens the beat's sheet, whose list (`BeatScenesList`) is the record. The list
  view lists each beat's scenes as links and the same "+N more"; the element
  page's SVG preview says how many scenes a beat has. Nothing is a store record
  or a row: the rendered test holds the serializer's output and the store's
  records equal with the cards shown, an integration test holds that a save of
  the shown board writes nothing, and the E2E walks the cards and the list by
  keyboard.
- **(C) The version gap is thirty minutes** (`SCENE_VERSION_MAX_GAP_MS`).

Fixed in review, each with a test that fails without the fix:

- **An imported heading too long to be a title was a 500**, and an import's
  refusals named one problem at a time. Scene titles went through
  `sanitiseManuscriptTitle` inside the text writer with no mapping, so a
  paragraph styled as a heading (over 200 characters) threw past the error
  handler. Now the server marks such a heading (`titleTooLong`, by the
  sanitiser's own bound), the proposed split keeps it as text, and a plan that
  makes one a title is refused `HEADING_TOO_LONG` naming the headings; every
  plan problem (`planProblems`) and every bound passed is answered at once.
- **A text save and a part or chapter deletion could deadlock.** The save wrote
  link rows before its scene row; the deletion's cascade takes the scene row,
  then its links. The save now takes its scene row (`lockSceneRow`) after the
  elements and before any link.
- **A spent rank gap was refused for good** (above).
- **The D3 guard could be passed by an alias.** It matched only
  `Identifier.method(` calls, so `const R = ManuscriptSceneRepository;
  R.setText(…)`, a destructuring, an index, a namespace import or a re-export
  carried a text method past it; it did not see a nested relation write
  (`chapter.update({ data: { scenes: { update … } } })`, or a research
  proposal's `scene: { update }`), nor a repository method other than the four
  putting `text` in its data; and it held only who takes the WRITER, so any
  module, a model-path one included, could take `saveSceneText` or
  `restoreSceneVersion` from the scene usecases and pass the guard. Each is now
  checked (and proved against planted sources): the repository objects are used
  only as `Object.readMethod` outside the writer and the repository; only the
  text methods write `text`; no nested write reaches either table; raw SQL
  inserting a scene or version, writing a version or setting `"text"` is
  refused (`MERGE`, `COPY` and a schema prefix included); and the four
  text-writing usecases are taken only by their own route handlers.
