## Design

```
accept a slot's beat ──► names lock → order lock (enrichment-review.ts)
   placement absent ──► slotChangeOf(session)   (story-slot.ts, under the order lock)
                          null        → rankForTarget(after, before)       placed between the two
                          a change    → 409 SLOT_CHANGED { change }         nothing written
   { unplaced: true } ─► created with its act, no rank                    "Accept without a place"
   { after, before }  ─► rankForTarget(after, before, act = slot's)        "Accept here"
view: slot { changed, choices (the act's placed beats, ≤ 100), choicesTruncated } → SlotPlacement

rankForTarget(element, { after, before, act })   (bible-order.ts; the move and every placement)
   readPlacedOrder (409 ORDER_SCOPE_TOO_LARGE past 10,000, never a cut read)
   neighbours named  → placeRank between them         (409 ORDER_STALE when not placed)
   none named        → a placed element stays where it is (an act change alone moves no rank);
                       an unplaced one goes to the end of the whole order (one free order: D25 as amended)
   exhausted         → rebalanceOrder (rebalancedRanks, one statement pair, audit row) → place again

lock order:  import → map → names → order → element → relation
   saveStoryMap / restore: map, then lockMapOrders (each ordered kind the map draws)
   deleteElement: maps, then the element      removeRelation: maps, then the relation

search read: element rows (no summary) ─ stored bytes of summaries, fields, notes, relation fields
             ─► chunks of ≤ fieldChunk elements and ≤ fieldChunkBytes ─► decrypt the chunk's text
                 (a relation's text once, with the first of its ends) ─► stop at the text budget
```

## Decisions

- **Refuse and ask (owner, #53 item 2).** The check runs under the order's
  lock, the one the placement takes, so what it judges is what would be
  written. "Changed" is anything that would make "between these two" false or
  ambiguous: a neighbour deleted or unplaced, either moved out of order or out
  of the slot's act, or a beat of that act now between them. The refusal
  carries a code only (`change`); the choices come from the review's own read
  (`slot.choices`), so no element name rides in an error body. "Choose where"
  is an explicit position on the acceptance rather than "accept unplaced, then
  drag": one transaction, and the beat is never seen unplaced by a reader who
  did not choose that. A position the author named that has since gone stale
  is ORDER_STALE, never a nearby place. The choices are capped at 100 beats of
  the act (`choicesTruncated`); past that the author picks the last and drags.
- **One beat a gap (#53 item 1).** A gap is taken while a beat for it is
  pending or accepted and still in the book: the prompt does not offer the slot
  again, and the validator refuses `SLOT_TAKEN` if a model proposes one anyway.
  As first built here the session then stopped asking about the gap; the owner
  replaced that the same day (below, "The session goes on with its beat").
- **Rebalance writes no version (#50 item 7).** Rule 1 is about changes an
  author (or an accepted proposal) makes to an entry; a rebalance changes no
  element's place relative to any other, so every reader of the order — the
  board, the timeline, the PDF, 4.2 — sees the same story before and after. A
  version per element would fill histories with entries nobody made and refuse
  every open tab's next save of those elements as a conflict. The moved element
  still gets its `movedInOrder` version, and the rebalance one audit row with
  the count. Older snapshots keep their old rank as history; a restore never
  applies a rank (3.2). The ranks are evenly spaced at the shortest length that
  leaves at least 36 keys per gap, so a rebalanced order takes about as many
  inserts per gap as a fresh one. The write is two statements (clear the
  order, then set it from an `unnest`), so no new rank meets an old one in the
  unique index halfway.
- **Across acts (#50 item 4).** As first built here, beats' story order was
  act first, then rank, and a beat with no neighbour named went to the end of
  its act. The owner replaced that the same day with one free order (below).
- **Lock order (#50 item 2).** The deadlock is real: the unique index on
  `(bookId, kind, orderRank)` is not partial, so a rank change takes the row
  FOR UPDATE, which a node insert's KEY SHARE waits on. Taking the order lock
  in the save makes the save queue on an advisory lock while holding no beat's
  row. `deleteElement` took its element lock before the map locks, which with
  the save (map → order) and a move (order → element) closed a three-way cycle;
  it now takes the maps first. The test holds the import's side by hand and
  watches the save wait on an advisory lock, then completes the swap.
- **Import ranks (#50 item 3).** Rather than check the capped read for
  truncation (which would refuse imports into long orders), the import asks
  only for the ranks it would write, by index; there is no cap to miss.
- **Search reads (#48 item 1).** Summaries, relation notes and relation fields
  are sized with `octet_length` (nothing decrypted) and read with the fields,
  chunk by chunk, so the text budget stops the decryption as well as the
  ranking. A relation's note and fields are read once, with the first of its
  ends to be searched, and kept for the other.
- **Phrases (#48 item 2)** stop at a line of plain text, which is a block (a
  paragraph, a list item, a line break the author typed in a summary).
- **Irregular forms (#48 item 3).** A word the table changes carries both
  stems, and a query term matches either; needles cover both stems, so
  skipping stays sound (the rank test compares results with skipping off).
  `SEARCH_ANALYZER_VERSION` moved to `analyse-3`.
- **The lockout flake (#48 item 4).** Reproduced by running the file beside six
  busy processes: four tests timed out at Jest's 5 s. Each makes up to 13
  bcrypt compares at cost 12 (about 260 ms each idle), and a timed-out test's
  attempts ran on into the next test's lockout reset, failing it too. The
  suite proves counts of compares and requested delays, which the work factor
  does not affect, so it hashes at bcrypt's lowest cost (the account's hash and
  the dummy alike); the same load then passes in 4 s.
- **The migration comment (#50 item 6)** was checked against Prisma 7.10: a
  migration file's statements are not one transaction (a failing statement
  left the earlier ones applied, and ADD VALUE then an INSERT of the value in
  one file applied). So `20261120500000_plot_beat_kind`'s header is wrong to
  say Prisma applies a migration file as one transaction. The file is NOT
  edited: an applied migration's checksum is part of its record, and
  `prisma migrate dev` asks to reset any database whose applied file changed.
  This note is the correction; the file's own reasoning still holds, since the
  story order's CHECK compares `kind::text` and would pass inside one
  transaction too.

## Owner amendments (2026-11-20)

Two of D25's parts were replaced by the owner after the two 3.H halves were
merged; D25's row in the roadmap records both.

```
"What happens between these?" after its beat is proposed
   interview-state: pending subject stays   name = the beat's, stored = its proposed fields
                                            (+ the created element's, once accepted); never challenged
   reconcile: element block not_yet_created.proposed_as; no slot block
   validate: an ADD on it ─► FIELD draft `toSlotBeat` (UPDATE / REMOVE: SLOT_BEAT_ADD_ONLY)
   persist:  FIELD row, elementId NULL, targetProposalId = the beat's proposal, baseVersion NULL
   accept:   beat PENDING ─► 409 END_NOT_CREATED       beat REJECTED / element gone ─► 409 END_GONE
             beat created ─► the element's lock, its version, the op still fits ─► one version naming the answers

one free order
   rankForTarget:     neighbours named → between them; none → the end of the whole order
   moveElementInOrder: a placed beat with no neighbour named keeps its rank, whatever its act
```

- **The session goes on with its beat.** The beat stays what the session is
  about: its questions are still filed `aboutPending`, so the scope the page
  names is the one the session started with, and nothing about a session
  changes when the author accepts the beat in the middle of it. What the
  proposal already fills counts as stored (rule 5), and once the beat is
  accepted its element's fields do too, so a field filled since is not asked.
  A field the beat holds is never CHALLENGED in this session: a challenge would
  have to propose an UPDATE of a value nobody has accepted yet. The further
  fields are FIELD proposals that name the beat's proposal rather than a new
  kind: they are reviewed, sanitised, encrypted, cited and decided exactly as
  any field proposal, and the CHECK holds their one difference (no element, no
  base version, ADD only). They wait for the beat as a new relation's end
  waits for its element, with the same two refusals, and are never offered for
  bulk acceptance (each is decided once its beat exists). The session finishes
  when its frontier is empty, the ordinary FRONTIER_EMPTY.
- **One free order.** The rank is the story order. The act-then-rank reading
  and the "end of its act" placement are gone (`actIndex` with them), so a beat
  may stand before a beat of an earlier act, as the author drags it. A drop
  into an empty lane names no neighbour, so it changes the act and leaves the
  beat where it stood in the order; a beat with no place yet and no neighbour
  named goes to the end. The plot board's lanes are unchanged: each is its
  act's beats in rank order. A slot is still two beats adjacent in one lane, and
  a slot's beat placed "between" them takes a rank between theirs.
