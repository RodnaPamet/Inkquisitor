# 2026-11-19 — 2.2 Question engine

**Commit:** uncommitted (branch `wip/2.2`, cut from `main` at `e34e1a1`; 2.1 is
built in parallel and is not on this base)

The question engine as a pure, testable core plus a model step behind an
interface. The interview algorithm is ported from the MIT-licensed
mattpocock/skills grilling skill (credited in `NOTICE`); the design is the
staged `design/QUESTION-ENGINE.md` (branch `wip/content`), whose 2.2 parts are
built here and whose 2.3 / 2.5 parts are left as seams. The packs and the
coverage evaluation set are the staged original content (written for
Inkquisitor in the content formats v1), moved into the repository unchanged.

## Design

```
POST …/interviews ──► startInterview / nextRound
   tx 1 (session advisory lock)    loadInterviewState → computeFrontier → planRound
                                   stop? → endSession(reason, stopDetail)            (no model)
                                   generator.wired? else 503 MODEL_NOT_WIRED          (nothing written)
                                   InterviewRound GENERATING (the claim) + plan JSON
   no transaction                  produceRound:
                                     buildGenerationRequest (system: product text; user: fenced author text)
                                     QuestionGenerator.generateCandidates            ◄── model-seam.ts (2.1)
                                     parseGeneratedQuestions (item by item) → sanitise → validateCandidate
                                     embed (2.0 provider) → findQuestionNeighbours (2.0 vector store)
                                     dedupe → fillGapsFromPack → orderRound → positions
   tx 2 (lock)                     questions (sanitised again, encrypted) → round OPEN, metrics, audit
   tx 3                            question vectors (a failure degrades; never undoes the round)

answer / skip / decide-later  ──► Answer row, next revision (append-only), round must be OPEN
close round N                 ──► every question has a status (or skipUnanswered) → CLOSED → roundsRun+1
                                   → stopNow: FRONTIER_EMPTY | NOTHING_AT_DEPTH | ROUND_BUDGET, or stay ACTIVE
stop                          ──► STOPPED, AUTHOR_STOPPED; answers kept
```

**The frontier** (`src/lib/interview/frontier.ts`) is the content formats'
rule 1.9 per field reference `(elementId, fieldKey)`: already-answered checks
first (the bible's stored values always, then any pluggable
`AlreadyAnsweredCheck`), then this session's answers (ANSWERED satisfies,
any status touches), then depth and prerequisites. Every open field off the
frontier is explained (`TOO_DEEP`, `WAITS_ON`, `WAITS_ON_DEFERRED`,
`TOUCHED`), which is what `stopDetail` reports. It reproduces the
`targetsAnyOf` of all 176 craft evaluation cases exactly.

**The model step** is `QuestionGenerator.generateCandidates(request)`; the
request carries the prompt, the strict output schema
(`GeneratedQuestionsSchema`), the tier, the purpose, the prompt version and
the per-call output budget. The model words questions; code decides everything
else. **The wiring seam is `src/lib/interview/model-seam.ts`, and only it**:
replace `fenceData` (placeholder) with 2.1's, make `defaultQuestionGenerator`
return a generator over `callStructured(request.schema, …)` with
`wired: true`, and make `modelBudgetSignals` return 2.1's kill switch and
spend-ceiling state. Until then every request that would generate refuses 503
`MODEL_NOT_WIRED` before writing.

## Decisions

- **Permissions.** `bible.edit` runs an interview (start, next round, close,
  stop, answer, skip, decide later); `bible.view` reads interviews. An
  interview is how the bible is written to (2.5), and its text is the bible's
  kind of text, so it follows the bible's two keys.
- **Deduplication uses the vector store**, where the design (written before
  2.0) said "without embeddings". The design's MinHash `shingles` column and
  `BookQuestionIndex` table are not built: book-wide comparison reads earlier
  sessions' questions about the same elements (bounded), the keyed
  `dedupeKey` index catches an exact repeat beyond that read, and the vector
  store's neighbours (stub embedder in tests) catch rewordings. Questions are
  embedded as `query` on both sides.
- **Two refinements of the duplicate rule.** A question about another element
  is never a repeat ("what does this character want?" asked of two characters
  is two questions; with element names stripped, the design's `exact` rule
  would have dropped every KIND session's second element). `sameShape` applies
  to CHOICE / EITHER_OR (half the options equal) and SCALE (equal anchors)
  only: two OPEN questions on one field are not duplicates for their kind
  alone, or a reopened field could never be asked again in a later session.
- **Core fields lead the frontier**, optional ones follow, each in template
  order. Consistent with the formats (which grade core keys only) and keeps
  the round cap from being spent on optional fields first.
- **A candidate names its element** (`elementId`): a KIND or BOOK round spans
  several elements, and the design's output schema had no way to say which.
- **Candidates carry no `dependsOn`.** The model cannot declare an order: code
  enforces it through the frontier (prerequisites from the template, whose
  schema is acyclic; a cycle or dangling prerequisite is unreachable, the
  second line). `Question.dependsOnQuestionIds` is derived for display and
  audit: the questions whose ANSWERED answers settled the prerequisites.
- **Answers are revisions.** The design had one answer per question; the
  brief's "a re-answer is a new row" is an `Answer` per revision
  (`@@unique([questionId, revision])`), the latest being the answer, allowed
  only while the round is open. The table is append-only by trigger.
- **Closing needs every question to have a status**, or `skipUnanswered`
  (SKIPPED rows, the author's act). The next round is a separate call: close
  needs no model, so it can end a session (and say why) even unwired.
- **Stop precedence** (`stopNow`, the one place it is decided). 2.1's kill switch and ceiling first, then the
  frontier's reasons, then the token and round budgets — when the rounds are
  spent AND nothing is left, FRONTIER_EMPTY / NOTHING_AT_DEPTH is the more
  useful answer. A round that produced no question pauses the session with
  `PROVIDER_FAILURE` (every call failed) or the new `NO_ACCEPTABLE_QUESTION`;
  the next round resumes. There is no FAILED session status.
- **Rule 6.** Progress over zero questions is `NOT_ASSESSED`; a KIND or BOOK
  scope with no element is refused `SCOPE_EMPTY` rather than "completed"; the
  coverage report over no session is `NOT_ASSESSED`.
- **Issue #23, item 1, for this source.** `vector_embedding_require_source`
  (generic; attached for `Question` with a `WHEN` clause) takes a KEY SHARE
  lock on the source row before a vector insert: a concurrent delete then
  waits and its delete trigger removes the vector; a source already gone, or
  one a delete holds, is refused (`VECTOR_SOURCE_MISSING`) on a plain write
  and skipped on a rebuild write (`rebuildGeneration` set). The lock is taken
  `SKIP LOCKED`: a vector write never waits on a source row, because a
  multi-row write waiting on a cascade that waits on it is a deadlock (40P01,
  measured, with the purge or element delete as the victim). A vector whose
  delete is rolled back is then missing until it is written again
  (deduplication degrades to its lexical signals). The table is named with
  the trigger's own schema, never the caller's `search_path`. A rebuild
  counts what its statement wrote (`RETURNING`), so a skipped vector is not
  counted as inserted. `rebuildQuestionEmbeddings` reads its
  source lazily, page by page, after the rebuild's start point (item 2), stops
  rather than writes a partial page, and passes `allowEmpty` only when the
  workspace has no question. The 2.0 tests that used `sourceModel: 'Question'`
  as an arbitrary name now use `FixtureNote`.
- **Re-checked at persist.** No lock is held while the model words a round,
  so the persist step reads the book again under the session lock: a field
  the author filled meanwhile is not asked (rule 5), an element deleted
  meanwhile is not asked about (its foreign key would otherwise fail the
  round), and a challenge whose quote left its stored value is dropped. When
  nothing is left, the session stops for what the book now says.
- **One question per field per round**, enforced after deduplication
  (`TARGET_ALREADY_ASKED`), so a round never exceeds its cap and its one
  challenge however many questions the model words; the session reads
  (`SESSION_QUESTIONS_MAX`, and `SESSION_ANSWERS_MAX` with
  `ANSWER_REVISIONS_MAX`, 20 a question) are held to the product of those
  bounds by a test.
- **The book's dedupe index is asked for the round's own candidates** (and
  the pack examples that could fill its gaps) through
  `RoundDeps.findExactRepeats`, one grouped read: an exact repeat beyond the
  bounded read of earlier questions is found by key.
- **Tokens travel with the output.** `generateCandidates` returns
  `{ output, tokensUsed }`, so the session's `tokensUsed` (what TOKEN_BUDGET
  reads) is charged from the seam alone, also when the round is then
  dropped.
- **Vectors after the commit.** A vector-store failure never undoes a round
  the author can see; it degrades later deduplication to its lexical signals.
- **Packs are read from disk** at `process.cwd()`, as inflect reads its skill
  corpus, and the Dockerfile copies the directory: they stay readable
  Markdown. A production server loads them at boot and exits 1 when they do
  not load; a request loads them before it writes anything. 2.2 checks their structure; the text scan, content-hash pins and
  evaluation-record gating are 2.3's.
- **The coverage evaluation** runs the product's `produceRound`. It counts
  only the generator's own questions as coverage (the pack fallback would let
  any generator pass), counts each candidate the engine dropped as an
  attempted behaviour, answers a two-field question only when the author
  knows both, and lists the behaviours a judge must grade as `ungraded`.
- **One persona at most** (CHECK `cardinality(personaKeys) <= 1`); the
  round-robin assignment for several is built and tested in the pure core for
  2.3, which widens the CHECK.
- **The migration is `20261119600000`**, so it sorts after 2.1's
  `20261119500000_ai_model_layer` when both land.
