# 2026-11-21 — 4.0 Source library and ingestion (D23, D26)

**Commit:** uncommitted (branch `wip/4.0`, cut from `main` at `1b0f9e2`)

An author uploads their own drafts, notes and earlier books — to a book's
library, or to the workspace's series library that books opt into. Each file
is read in the request and kept only as encrypted passages; once the author has
seen the cost and confirmed it, a background job embeds the passages and draws
facts from each one with a fast-tier call. Code checks every fact's quote
against its passage; the author confirms or rejects each fact, one by one or in
bulk over what the page showed. Only a confirmed fact counts as answered: the
question engine's frontier no longer asks the field it answers.

## Design

### Re-ingesting a changed file

No file is kept, so "re-ingest" is a new upload. The same text twice in one
library is refused (`SOURCE_DUPLICATE`, the keyed content hash under a unique
index). A changed file under a name the library holds is a new `Source` with
the next `version` and `supersedesId` naming the newest of that name; the old
one stays, its confirmed facts still counting, until the author removes it.
When the new version's extraction draws a fact with the same predicate, the
same subject (name key) and the same quoted passage (folded) as a decided fact
of the version it supersedes, the new fact takes that decision
(`carriedFromFactId`). Everything else is pending again. Kept simple on
purpose: no diff, no automatic removal of the old version.

### In-interview confirmation (what 4.0 does, and does not)

D23's "Your draft says X (ch. 3). Is that canon?" is served by the Facts page:
each fact is quoted with its passage and confirmed in place. 4.0 adds no
confirmation question to an interview — that is 4.4's source-question
generator. What 4.0 guarantees in the interview is the half that matters for
rule 5: a pending or rejected fact answers nothing; a confirmed one (or a
book's override of an inherited one) removes its field from the frontier as
the `source-facts` check, and the scope's confirmed facts and most relevant
passages reach the question generator as fenced context.

## Decisions

- **Parse in the request, embed and extract in the job.** The file may not be
  stored, and a job payload carries ids only, so the bytes must be read where
  they arrive. Parsing is bounded by size, `readZip`'s limits, the entity
  refusal and the PDF worker's heap limit and deadline; embedding and the
  model calls (the slow, spending part) are in the job.
- **The PDF reader is `unpdf`** (MIT; its serverless build of pdf.js,
  Apache-2.0), run as plain ESM in a worker thread, `isEvalSupported: false`.
  inflect carries `pdf-parse` 1.1.1, whose pdf.js is years old; not carried.
  **DOCX goes through mammoth** as inflect reads Word (used as a dependency,
  not a copied file, so no carve-manifest row), but only after `readZip` has
  accepted the archive, and on a ZIP rebuilt from its entries.
- **No OCR** (D26): fewer than ten visible characters in the text layer is
  `SOURCE_NO_TEXT_LAYER`.
- **Chunk bounds** are 1,000–2,000 estimated tokens (four characters a token),
  cut at a heading of level 1–3 or a break; at most 1,500 chunks a source.
- **The estimate's "at most" is the budget.** It uses one token a UTF-8 byte
  and the full output budget per chunk; the author confirms it, the server
  refuses a confirmation below the remaining chunks' worst case, and the job
  checks every chunk against what is left of it with the same function, so a
  job never spends more than the author confirmed. The monthly ceiling is 2.1's
  own check before each call.
- **The rate limit is waited out in the job**, not failed: a background job
  has no caller to send a 429 to.
- **The predicate table is small on purpose**: a character's role, want and
  appearance, a setting's kind of place, a faction's purpose, membership and
  power base. A trait does not answer a list of traits; a backstory sentence
  does not answer a wound. Unmapped facts are still shown and still reach the
  question generator as context.
- **A series fact is linked per book at read time** by the book's element
  names (name key, unique); only a book library's fact stores its subject
  link. An override answers the same field for its book.
- **Bulk confirm** is a signed token over exactly the offered ids, the view,
  the reader and the time (one hour), under the workspace's subkey; the server
  also re-reads each fact (still pending, unflagged, in the view). Flagged facts
  are never offered.
- **Permissions reuse `bible.view` / `bible.edit`**: sources are bible
  material, and the owner's rule (OWNER and EDITOR write, READER reads) is
  exactly those keys.
- **Progress is polled** (the source's GET every two seconds while it runs),
  not streamed: no stream slot is held for a job that can run for an hour.
- **Search (3.4) does not read chunks** in 4.0. A library may hold a few
  million tokens; D21's decrypt-and-scan would break search's budget, and a
  separate, bounded result group needs its own design. Deferred.
- **Retention**: a source, its chunks, facts, vectors and overrides live until
  the author removes the source; they go with their book's purge and the
  workspace's deletion by cascade. Nothing is kept after removal.
- **A round's context is read in its claim's transaction, lexically.** Reading
  it in a transaction of its own added a round trip before the first question
  (`interview-latency.test.ts` holds that count); embedding the query inside the
  claim would put a provider call inside a transaction. So the interview gets
  confirmed facts and 3.4-ranked passages; the retriever's vector candidates
  join when a caller holds a query vector (tested), which 4.1's retrieval work
  can supply.
- **QUESTION_PROMPT and REPHRASE_PROMPT** gained one line naming the new data
  blocks (versions `question-generation.4.0.0`, `question-rephrase.4.0.0`);
  every pack record and the rephrase record were re-run.
