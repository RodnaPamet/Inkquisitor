## Design

### Restorable scenes (issue #71)

```
deleteScene ─► deletedAt = now (the DB's clock) ── hidden: every read asks LIVE ── kept: text, note, card, links,
                                                   versions, draft facts, mismatches, thread links, research proposals
   │  ≤ 30 days: Recently deleted ─► restoreScene ─► its rank if free (partial unique over live scenes), else end of chapter
   └─ > 30 days: daily scene-purge (owning role) ─► DELETE scene (cascade) ─► its book-keyed versions ─► audit under RLS
```

The scene row stays; everything keyed to it stays with it, so a restore rewrites nothing but `deletedAt` and, when
its place was taken, its rank. Hiding is done at the reads: `ManuscriptSceneRepository` asks `LIVE` everywhere,
link/card/mismatch/thread-link/research-proposal/scene-session reads ask `OF_LIVE_SCENE`, and the raw SQL of the
draft reading's discovery and due scenes, the prose checks and the deep check's draft facts asks `"deletedAt" IS NULL`.
A save of a deleted scene finds no scene (404), and `lockSceneRow` refuses it.

The scene's versions carry no foreign key (5.1: the history outlived a hard-deleted scene). The owner decided the
history goes with the purge, so the append-only trigger gained ONE branch: the scene row is gone AND the transaction
names that scene in `inkquisitor.scene_purge`. app_user holds no DELETE on the version tables, so the purge runs as
the owning role (`scene-purge`), then binds the workspace's RLS for its audit row — the sign-up pattern.

`manuscript_scene_delete_only_when_purge_due` mirrors the book's trigger, its one other admitted delete the CHAPTER's
cascade (recognised by the chapter row being gone, as the book's trigger recognises its workspace's). A deleted
chapter therefore takes its recently deleted scenes, and its 409 NOT_EMPTY counts them (`recentlyDeleted`), so the
author confirms what goes.

### Full deletion within 30 days (D36)

```
OWNER, exact name ─► Workspace.deletedAt ─► gate / claims / first workspace: missing; dispatchers: dropped; jobs: removed
   │  ≤ 30 days: /no-workspace lists it ─► an OWNER restores it whole (account deletion cancelled)
   └─ > 30 days: workspace-purge ─► storage objects ─► jobs ─► [owning role, one tx] lock ─► DELETE row (cascade)
                                     ─► the account (asked, no membership left) ─► WORKSPACE_PURGED on its own chain
```

Every workspace-scoped model already cascades from `Workspace`, and the append-only triggers already admit the
workspace's cascade (they test "the workspace row is gone"), so the purge is one DELETE; nothing failed when it was
first run. Objects and jobs go FIRST: a failure there stops that workspace's purge (due again tomorrow) rather than
leaving objects or jobs nothing could find again. app_user may never delete a workspace row (trigger), so no request
path can.

### The full export (D36)

One WinZip AES-256 (AE-2) zip, written by `@zip.js/zip.js` (fflate has no encryption; zip.js is the maintained,
BSD-3 library that writes AES zips) with workers off, streamed into the response through a joined pipe with
backpressure; a cancelled response makes every later write refuse. Each table is a JSON Lines entry read a page at a
time, each page its own short transaction (the encryption extension decrypts; RLS bounds). The layout is one table
(`archive-layout.ts`); the README is generated from it and the integration test holds the archive and the README to
each other.

### Word search over scenes

`readSceneDocuments` beside the bible's read: live scenes sized by stored bytes (title, text, note), decrypted a chunk
at a time under `SEARCH_SCENE_TEXT_MAX_CHARS`, a budget of its own so a large bible cannot starve the manuscript. The
text is `HtmlTextReader`'s, the very text the editor's map rebuilds, so a snippet's offsets are editor offsets:
`APP_ROUTES.sceneAt` carries `?at=&len=` (never the query) and the editor selects and scrolls to the match.

### D3 in words, and the derived guard

Settings → "How Inkquisitor uses AI", and a line under the outline and in the scene editor, from the catalogue's
`aiUse`. The D3 guard's model modules were a fixed list plus seams found by NAME; they are now every direct importer
of the model core (the SDK's file, `callStructured`, the server-tool loop, the stub, the ledger-bound call), from the
import graph, and a test holds that the derivation contains every seam the old rule found and every module that calls
`clientForRun` / `callStructured` / `runServerToolLoop`.

### The backup and restore drill

`docs/backup-restore.md` is the runbook; `backup-restore-drill.test.ts` runs it in the integration suite: `pg_dump
--format=custom` of the database, `pg_restore` into a fresh database, then a client built by `createDatabase` reads the
workspace back. CI's Test job runs the tools inside `ci-postgres` (`PG_TOOLS_CONTAINER`), so they are the server's
own; locally they come from PATH and their major version is checked.

## Decisions

- **A deleted scene's machine state is KEPT, not discarded.** Clearing draft facts, mismatches and the prose check at
  deletion would have needed fewer filters, but would have lost decisions the author made (a BOTH_TRUE explanation is
  a fact naming its mismatch) and made "restored whole" untrue. The cost is the live-scene filters on every read;
  `scene-restore.test.ts` walks the lists.
- **The chapter's cascade passes the guard.** A chapter's deletion is immediate (5.1); its recently deleted scenes go
  with it, counted in the confirmation. Making a chapter soft too is a larger change than #71 asked.
- **Workspace restore is an account route.** A deleted workspace has no context a request can enter, so the list and
  the restore are `/api/account/deleted-workspaces/**` (`getUserCtx`), the membership read under the closed
  `workspace-deletion-discovery` bypass and the restore itself inside the workspace's own context.
- **The audit trail is kept, and records the purge.** It has no foreign key by design and holds no author text; the
  workspace's own chain ends with WORKSPACE_PURGED. AiCallLog goes with the workspace (its trigger already admits
  the workspace's cascade; it holds no text, and its retention is a maximum, not a minimum).
- **The account is deleted only when it holds no membership at the purge.** Joined another workspace meanwhile:
  kept (`workspace-deletion.test.ts`).
- **Sources are exported as their kept chunks.** The file is never stored (4.0); the chunks are the author's material.
- **The export is in the request.** A job would need the passphrase in its payload or the archive stored unencrypted.
  Streamed with backpressure, memory holds one page and one manuscript; a large export takes time, not memory. Books
  in Recently deleted are not exported (restore first). Past 500 books it is refused, by name.
- **A scene's card is not searched.** Four short fields about the scene, which a later subphase can add with its own
  source kind; title, text and note are.
- **Two new permission keys** (`workspace.export`, `workspace.delete`), OWNER only, rather than reusing
  `workspace.manage`: the whole workspace's data and its end are their own decisions.
- **zip.js 2.25.0**, the newest release at least two weeks old; listed in NOTICE and as a server external package.

## Load numbers

`npm run test:load` on the development machine (PostgreSQL 16 on localhost), 2,000 elements, 20,000 versions and a
150,000-word manuscript, 30 runs after 3 warm-ups, word search's bound 1,000 ms at p95:

| Read | p50 | p95 |
| --- | --- | --- |
| search (common word) | 671.5 ms | 849.1 ms |
| search (a name) | 617.1 ms | 768.0 ms |
| search (a word all through the manuscript) | 689.6 ms | 918.4 ms |

The manuscript adds a few hundred thousand characters to a read that was already the whole bible; the scenes' own
budget (8,000,000 characters) is far above a 150,000-word manuscript (about 900,000).
