# 2026-11-19 — 1.x follow-ups: the PDF's Unicode font, the concept-note slug clash

Two Phase 1 follow-ups, each an owner decision of 2026-11-19: issue #24 (the
bible PDF printed every non-WinAnsi character as `?`) and issue #27 item 3 (a
concept note could overwrite an existing RESEARCH element). A third owner
decision is recorded here: the RESEARCH template's optional rich-text
**Notes** field, which 1.3 added and flagged, is approved and stays.

## Design

### 1. Noto Sans in the PDF (#24)

```
createPdfDocument ─ new PDFDocument({ font: '' })   no default font: Helvetica is never loaded or embedded
                  └ registerPdfFonts(doc)          Body / Body-Bold from <cwd>/fonts/noto-sans/*.ttf (bytes read once per process,
                                                    parsed per document)
every text draw ── drawableText(s) = toPdfText(s, pdfFontCovers)
                     NFC → drop controls (tab → space) → per grapheme cluster:
                       every code point covered (format characters the font lacks dropped) → drawn as itself
                       otherwise                                                           → one U+FFFD
pdfkit + fontkit ─ embed a SUBSET of each font (only the glyphs drawn), Identity-H, with a ToUnicode CMap
```

**The font.** Noto Sans 2.015, unhinted, regular and bold, from
`github.com/notofonts/notofonts.github.io` at commit
`ebbf5a34c2aaac39770e02d24afcfe9a8ad55e3e` (`fonts/NotoSans/unhinted/ttf/`),
the release `NotoSans-v2.015` of `notofonts/latin-greek-cyrillic`, whose
`OFL.txt` (at that tag) sits beside the files. Each file's name table says
`Version 2.015`.

| File | Bytes | sha256 |
|---|---|---|
| `fonts/noto-sans/NotoSans-Regular.ttf` | 431,364 | `f3961a9cde016d41a4879aecda1474d3a36d6bf54fa0e4643de029cc2248b0e8` |
| `fonts/noto-sans/NotoSans-Bold.ttf` | 432,376 | `87cb2d84472a7d66da659ee47b6cdb9552326e8c128245231f191b6ac72529d9` |
| `fonts/noto-sans/OFL.txt` | 4,396 | `cee9892f9f0cc8fe882c9e9537ee6a89621d86ee7ceaf70b02e2b2b1c25c061a` |

0.86 MB in all, under the 1.5 MB target. Both weights cover the same 2,965
code points: Basic Latin, Latin-1, Latin Extended-A and -B, Latin Extended
Additional and IPA in full, the Greek letters of Greek and Coptic and of Greek
Extended, Cyrillic with its Supplement and Extended-A and -B, and U+FFFD. They
cover no Coptic letters, no CJK and no emoji. The PDF uses no italic, so none is carried.

**The fallback for what the font cannot draw: one `�` (U+FFFD) per
user-perceived character.** Of the two options the brief allowed, the
replacement character was chosen over a "(not shown: N characters …)" note
because it keeps the position and the amount of what is missing in the line
where it was, and it is the same rule in every place text is drawn (cover,
running header, headings, values, relations); a note would need a second
place to put it in a heading or a header. "Character" is a grapheme cluster
(`Intl.Segmenter`): a skin-toned, flag or family emoji is one mark, two CJK
characters are two. A cluster is drawn only if the font covers every code
point in it; variation selectors, joiners and tag characters the font lacks
are dropped instead of failing their cluster, so `©` + VS16 prints `©`.
Nothing can crash: any string becomes drawable text (a lone surrogate is a
`�` too).

**The text layer round-trips.** PDFKit writes a ToUnicode CMap for each
embedded font, mapping each glyph to the characters it was drawn for, so
copying, searching and extracting give back the author's text. Noto Sans maps
no two code points to one glyph (checked over its whole cmap), so Cyrillic,
Greek and Latin look-alikes stay distinct. `tests/helpers/pdf-text.ts` was
rewritten to read it that way: objects through the cross-reference table,
pages in `/Kids` order, `Tf` / `TJ` in each page's content stream, glyph ids
through the selected font's ToUnicode map. It refuses a font with no map, so
a standard font sneaking back in fails every PDF test.

**Packaging.** `pdfkit` and now `fontkit` (a direct dependency at pdfkit's own
`^2.0.4`, one copy in node_modules) are server external packages. The font
files are not a package: `src/lib/pdf/fonts.ts` reads them from
`<cwd>/fonts/noto-sans`. `next start` (the E2E server), the worker and the
test runners run from the repository root, and the image's processes from
`/app`, where the runner stage now copies `fonts/`. The repository has no
standalone output, so there is no `.next/standalone` to trace into. The worker
builds no PDF today, but it runs from the same `/app` and would find them.

## Size

`renderBiblePdf`, same inputs, same machine (bytes):

| Bible | Helvetica (before) | Noto Sans subset (after) |
|---|---|---|
| The test fixture (4 elements) | 6,085 | 15,843 |
| The fixture plus 60 characters with summaries | 25,398 | 39,821 |
| The fixture with Cyrillic, Greek, CJK and emoji names | — (printed `?`) | 18,824 |

The difference is the two subsets, about 5 KB each for a Latin-only bible
plus a few KB a script; the whole file would be 430 KB each. A test holds the
fixture's PDF under 60 KB, so embedding a whole font fails it. The 100,000-
character unbroken run lays out in about 0.7 s (the test's bound is 2 s).

## Determinism

The export was deterministic before (fixed `CreationDate`, the file id derived
from the info dictionary) and still is: PDFKit names a subset from the font's
id in the document (`F1` → `BZZZZZ+NotoSans-Regular`), and those ids are
given in order of first use. A new test renders the fixture twice and compares the bytes. No
existing test pinned PDF bytes.

### 2. A concept note never overwrites (#27 item 3)

```
POST …/import/concept-note { text, name?, slug? }
  slug supplied ─ taken (any kind)? ─ yes → 409 SLUG_TAKEN, nothing written
               └ no → create at it
  slug derived  ─ freeSlug(slugify(name) || 'concept-note')   first candidate not taken: my-idea, my-idea-2, …
               └ create there; a concurrent create that took it → retry in a fresh transaction (up to 8, as createElement)
  → always { outcome: 'created', versionNumber: 1 }, 201
```

The note never reads, locks or changes an existing element, of any kind. A
derived slug another KIND holds is passed over the same way, where 1.3
refused it `KIND_CONFLICT`. The Markdown bundle keeps its 1.3 rule: elements
are matched by slug and a repeat import writes nothing.

## Decisions

- **Re-importing the same note makes a duplicate.** That is the owner's
  accepted cost of never overwriting: an author who pastes a note twice gets
  two RESEARCH entries (`my-idea`, `my-idea-2`) and deletes one, with undo,
  rather than losing an edited note to a paste. The modal's description says
  so.
- **A supplied taken slug is `SLUG_TAKEN`, whatever holds it.** Before, a
  RESEARCH holder was updated and another kind was `KIND_CONFLICT`. With no
  update path, the kind no longer matters; the answer is the one a manual
  create gives, from the same `slugConflict()`. The modal sends no slug today,
  so only an API caller meets it.
- **The report's `outcome` is the literal `'created'`.** The type says what
  the usecase can return, and the modal's `updated` / `unchanged` note
  messages, which nothing can reach any more, are removed from the catalogue.
- **`freeSlug` moved to `bible-common.ts`**, so `createElement` and the note
  ask the candidates the same way, and race the same way.
- **The RESEARCH `notes` field is approved** (owner, 2026-11-19), as 1.3
  added it: rich text, optional, last.
- **Unhinted rather than hinted builds.** Hinting is TrueType instructions for
  screen rasterisation at small pixel sizes; a PDF viewer scales the outlines
  itself, and the unhinted files are 30% smaller (431 KB against 622 KB).
- **One rule for every weight.** The coverage is the intersection of both
  weights' cmaps, so a character is never drawn in one weight and replaced in
  the other (today they are identical).
- **fontkit is asked directly, not through PDFKit's internals.** Its
  `characterSet` is what PDFKit's embedding resolves glyphs through, so the
  coverage test and the drawing agree; importing it costs one line in
  `package.json` (it was already installed for pdfkit) and a declaration file.
- **Each document parses its own font.** fontkit caches glyph objects, and
  their `codePoints`, on the font object; PDFKit writes the ToUnicode entry
  from the first sighting of a glyph. A font shared across documents would let
  one export's text decide another's text layer, so only the bytes are shared.
- **Ligatures stay on.** fontkit gives a ligature glyph the characters it was
  formed from, so `office` drawn with the `ffi` ligature reads back `office`.
  An author's own `ﬁ` (U+FB01) and a formed `fi` share a glyph, so in a
  document holding both, the text layer gives whichever came first for both;
  not worth losing ligatures for.
- **No start-up check for the font files.** A missing file fails the PDF
  export alone, with the path in the error; refusing to start the web tier or
  the worker over one export would be out of proportion. The image layout test
  is the guard that they are there.

## Left to file

- The image itself was not built here (no Docker daemon in this
  environment). `tests/unit/pdf/pdf-fonts.test.ts` lays a directory out from
  the runner stage's own `COPY` lines and loads the fonts from it, and CI's
  Docker job builds the image; a smoke run of the built image's PDF export
  would close the last gap.
- Scripts beyond Latin, Greek and Cyrillic (CJK, Arabic, Hebrew, Devanagari,
  emoji) print as `�`. Covering them is a font fallback chain (Noto Sans CJK
  alone is about 16 MB a weight before subsetting) and right-to-left layout;
  it belongs with Phase 6's publishing exports.
