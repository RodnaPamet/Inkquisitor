# 2026-11-19 — 1.1 Book and element model

## Design

The bible is five workspace-scoped tables (`prisma/schema/bible.prisma`):

```
Book ──< BibleElement ──< BibleField          (one row per filled template field)
  │           │  ▲
  │           └──┴── BibleRelation            (from → to, typed; stored once, read from both ends)
  └──< BibleEntryVersion                       (append-only; keyed to the BOOK, names its element)
```

- **Kinds are closed** (`BibleElementKind`, 15 values). Each kind's fields and
  relation types are an original JSON template in
  `src/lib/bible/templates/<kind>.json`, copied in from the reviewed content
  staging and parsed with a Zod schema when the registry
  (`src/lib/bible/templates.ts`) loads. The schema holds the cross-field rules
  too: unique keys and labels, orders 1..n, `dependsOn` naming only EARLIER
  fields (so no cycle can exist), relation targets of the template's own kind
  or a later one, `related_to` built in and never declared. A broken template
  stops the module loading, so it fails every test and the build rather than
  a request.
- **The workspace travels in every foreign key.** An element references its
  book by `(workspaceId, bookId)`, a field its element by
  `(workspaceId, elementId)`, a relation both its ends by `(bookId, elementId)`.
  On top of RLS, the database itself refuses an element under another
  workspace's book and a relation between two books, whoever writes.
- **Field values** are checked against their field's type and sanitised in
  one place, `normaliseFieldValue`: text and list items through
  `sanitizePlainText` (one line), rich text through `sanitizeRichTextHtml`,
  choice against the option values, scale 1..5. An empty value clears the field
  (its row is deleted), so "filled" always means "has a row". Values are stored
  JSON-encoded, so the type survives the encrypted string column.
- **The versioned save** (`src/app-layer/usecases/bible-common.ts`). Every save
  of an element or its fields is one transaction: a per-element advisory lock
  (`hashtext('bible-element:' || id)`), the change, then `recordVersion`, which
  reads the element and its fields back inside the same transaction, builds the
  snapshot, and appends `latest + 1`. The lock serialises concurrent saves of
  one element, so numbers are distinct and consecutive and each snapshot is the
  state its own save left; the `(elementId, versionNumber)` unique index is the
  backstop. A restore applies an old snapshot as a new save and appends a
  version equal to it, with `restoredFromVersion`.
- **Append-only history.** `app_user` holds no `UPDATE`, `DELETE` or
  `TRUNCATE` on `BibleEntryVersion`, and a trigger refuses them for every role
  (P0001, `BIBLE_VERSION_APPEND_ONLY`). Two writes pass, both made by the
  database's referential actions: the delete its book's cascade makes (the
  trigger finds the book already gone, as the last-OWNER guard finds its
  workspace), and the `ON DELETE SET NULL` of a deleted author, where only
  `authorId` changes, to NULL, from a user who no longer exists.
- **Encryption.** `Book.logline`, `BibleElement.summary`, `BibleField.value`,
  `BibleRelation.note`, `BibleEntryVersion.snapshot` and `.changeSummary` are
  in the manifest. The snapshot is JSON serialised to a string column and
  sealed whole: the extension seals strings, and a `Json` column's leaves would
  pass it untouched.
- **Authorization.** `bible.view` (every role) and `bible.edit` (OWNER,
  EDITOR) replace the placeholder `content.*` keys. Every route is
  `withApiErrorHandling(requirePermission(key, …))`, every usecase asks
  `assertPermission` first, and every change writes an audit row (ids, counts,
  codes) in its own transaction.

## Decisions

- **A save that changes nothing writes no version.** The roadmap says a
  version is written "on every save"; read literally, an autosave (1.2) would
  fill the history with identical snapshots. A save is versioned when it
  changes the element or a field; a no-op answers with `changedKeys: []` and
  the current version number. A restore always writes one: it is an explicit
  act.
- **History is keyed to the book, not the element.** An element FK would have
  to cascade (the trigger refuses the delete) or set null (the trigger refuses
  the update). So `elementId` is a plain column, and deleting an element keeps
  its versions; they go with the book. This also leaves room for 1.H's
  soft-delete and an undelete.
- **Relations are not in the snapshot.** The brief defines the snapshot as the
  element plus its fields; relations are their own audited rows. A relation
  type is identified by the declaring kind plus its key (two kinds may each
  declare `allied_with`), and it is always stored from the declaring kind's
  element, so a lookup is `getRelationType(from.kind, type)`. A type whose
  label equals its inverse label reads the same both ways, so its reverse is a
  duplicate; a directed type may run both ways.
- **Titles, names, slugs and custom labels are not encrypted.** Lists sort by
  them, the slug is unique per book (a unique index over ciphertext would
  compare envelopes, not names), and the slug is derived from the name, so
  encrypting the name alone would hide nothing. Recorded here rather than left
  implicit; changing it is a decision about search and sorting.
- **Restore re-validates.** A snapshot is re-sanitised and checked against the
  kind's CURRENT template; a field the template no longer has, or whose value
  its current type refuses, is skipped and reported (`skippedFieldKeys`). The
  old slug is restored only if no other element has taken it since
  (`slugKept`).
- **Bounds.** Readable columns are bounded by CHECKs as well as the schemas;
  encrypted columns only by the usecase (their stored length is the
  envelope's). Raw input may be up to four times a bound before sanitising; the
  bound applies to what is stored.
- **The sanitiser guard is file-grained.** It proves every caller of a
  repository write method also calls the field's sanitiser, that there is one
  Prisma write path per model and no raw SQL write, and that each sanitiser
  reaches a `sanitize-html` primitive. That a `<script>` written through every
  path is stored stripped is the behaviour test
  (`tests/integration/bible-validation.test.ts`).
- **`sanitize-html`'s parser is ESM.** The unit and integration Jest projects
  now transform the cluster, as inflect-compliance's config does; Next and the
  worker bundle load it natively.
- **Element status and book stage are enums** (`DRAFT | IN_PROGRESS |
  SETTLED`; `CONCEPT | PLANNING | DRAFTING | REVISING | PUBLISHING`); genre and
  audience are free text for now.
