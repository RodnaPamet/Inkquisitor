# 2026-11-20 — 3.3 Interview from the canvas

**Subphase:** Phase 3.3 (roadmap section 4), owner decision D24 (with D11, D14,
D22). Not committed yet: the branch carries the change uncommitted for review.

Interviews start from a story map: "Grill this" on a selection, "Question this
relation" on an edge, "What happens between these?" in the gap between two
beats. A relation now holds FIELDS of its own, which the engine asks about, and
reconcile may propose new relations. What an interview proposes to ADD to the
book's structure is previewed on the map as ghosts beside a plain list, and is
created only when the author accepts it.

## Design

```
templates/<kind>.json   relationTypes[].fields (1..4, text | richtext)      related_to: nature, significance
BibleRelationField      one row per filled field (encrypted `value`)         RLS, workspace-led indexes
BibleRelationVersion    append-only history of a relation (snapshot, changeSummary encrypted;
                        source MANUAL | IMPORT | INTERVIEW, INTERVIEW names its answers)

"Grill this"            InterviewSetupSheet ──► scope SELECTION {elementIds, relationIds}
  (cards and/or edges)  resolveSelection: every id the book's (404), + every relation BETWEEN two
                        selected elements; nothing → SCOPE_EMPTY; > 60 relations → SCOPE_TOO_LARGE
                        frozen on the session (scopeElementIds, scopeRelationIds)
"What happens between"  scope BETWEEN {afterElementId, beforeElementId}: two placed beats of one act,
                        adjacent (SLOT_INVALID: SAME_ELEMENT | NOT_PLOT_BEATS | NOT_PLACED |
                        NOT_IN_ORDER | DIFFERENT_LANES | NOT_ADJACENT); the subject is the beat not
                        yet created (PENDING_SUBJECT_ID), its act answered by the slot (`between-slot`)

subjects                element id │ relation id (its fields, filed under its declaring end with
                        Question.relationId) │ PENDING_SUBJECT_ID (filed under the slot's earlier
                        neighbour, Question.aboutPending) — `subjectIdOf(question)` is the one map

reconcile               + relation-ends (the selection's elements and its relations' ends; a slot's
                        two neighbours, marked neighbour), relation-types, slot
                        output: operations (FIELD │ RELATION_FIELD │ the pending element's fields)
                                newElements[].fillsSlot, newRelations[] (ends: an id or `new.N`)
validate                NEW_RELATION: ends in scope or a passing new element │ not self │ type
                        declared by the from end's kind for the to end's (or related_to) │ not held,
                        not twice │ cites this run's ANSWERED answers, every end named in or asked
                        about by one │ note and fields grounded │ D14 flag
                        slot: SLOT_NOT_OFFERED │ SLOT_KIND_MISMATCH │ SLOT_TAKEN │
                        PENDING_WITHOUT_ELEMENT; the pending element's fields fold into its proposal

accept RELATION_FIELD   relation lock ─► baseVersion (409 VERSION_CONFLICT) ─► write ─► version (INTERVIEW)
accept NEW_ELEMENT      (slot) names lock ─► lockOrder ─► createElementInTx(fields + act)
                        ─► placeNewElementInOrderTx (both versions INTERVIEW, naming the answers)
accept NEW_RELATION     an end proposed as a new element must be accepted first (END_NOT_CREATED;
                        END_GONE when it was rejected or deleted) ─► createRelationInTx (v1, INTERVIEW)

story map               PendingStructureList (no tldraw, outside the canvas boundary) ─► GET
                        …/proposals/pending-structure ─► structure ─► StoryMapEditor ─► preview
                        ─► OnTheCanvas: LaneBackdrop + StructurePreviewLayer (ghost nodes, ghost
                        edges, slot controls), never store records
                        accept in the list ─► review route ─► AcceptedStructure ─► the editor adds the
                        card / draws the edge ─► the map's own save (version lock)
```

## Decisions

- **A relation's history is its own table, not its declaring element's.** A
  relation is one fact read from both ends; a relation change moving the
  declaring element's version would make an edit on the other end conflict
  with nothing it touched, an element restore would rewrite relation fields,
  and the history would go with the declaring element. `BibleRelationVersion`
  has its own advisory lock (`bible-relation:<id>`) and number sequence;
  `baseVersion` 0 means "no version yet" for a relation saved before 3.3 (the
  CHECK admits 0 only for a RELATION_FIELD proposal). Every relation the product
  creates now writes version 1 (the panel, an acceptance, an import).
- **One relations pack**, not a relation section per craft pack. The relation
  questions are the same craft whichever kinds a link joins, the coverage is
  every relation field key, and one pack has one evaluation set and one record
  (D11 applies to it as to every pack). A session pins it when its scope holds a
  relation.
- **Questions keep an element foreign key.** A relation question is filed under
  its declaring end with `relationId`; a pending one under the slot's earlier
  neighbour with `aboutPending`. A nullable element key would have meant an
  optional composite foreign key Prisma cannot spell beside the required book.
  `subjectIdOf` maps a row back to its subject everywhere (rounds, rephrase,
  dedupe neighbours, the UI).
- **NEW_RELATION only where the session offers relation ends.** An ELEMENT, KIND
  or BOOK session sends no `relation-ends` block, so a model naming a relation
  there is refused `RELATION_END_OUT_OF_SCOPE`. Ends may be a new element of the
  same answer (`new.N`), accepted first; the relation is stored from the
  declaring end and never turned round.
- **"Addressed by an answer"** (`RELATION_NOT_IN_ANSWERS`): every end must be
  named in a cited answer, or be the subject of a cited answer's question (or
  an end of the relation it asked about); a slot's neighbours are addressed by
  an answer about the slot. Rule 2
  applies to the link itself, not only its prose.
- **The slot's beat is placed by the 3.2 order move, under its lock, in the
  acceptance's transaction**, between the neighbours as they stand then; a
  neighbour moved or deleted since is an open end. Both versions — created,
  then placed — are INTERVIEW and name the answers. The names lock is taken
  first, then the order's, both before any element lock: the book's lock order,
  which the bundle import also follows (taking the order's lock first deadlocked
  against an import, found in review).
- **Ghosts are React, never records.** The ghosts are drawn in tldraw's
  `OnTheCanvas` from React state (like 3.2's lanes): nothing reaches the store, so
  the serializer, the save, the snapshot and the diff cannot carry one, and the
  layer takes no pointer events. It has its own error boundary: a failure draws
  nothing and the list says so. The list carries no tldraw and sits outside the
  canvas's boundary, so it works when the canvas does not load.
- **What is accepted from a map's list is added to that map**, through the map's
  own save under its version lock (a card for a new element of a kind the map
  draws; an edge for a new relation whose ends are both on it). An acceptance on
  the review page adds nothing to any map: a write the author did not make on a
  map would meet the version lock of every open tab; the element is in the
  bible and the picker adds it.
- **Research's FIT step stays ADD, UPDATE and NEW_ELEMENT.** Research has no
  relation ends of its own (its scope is a brief's elements), so it does not
  propose relations yet.
- **The bundle carries relation fields** (frontmatter `relations[].fields`, the
  type's template order), so an export loses nothing and the round trip stays
  byte-identical. An import sets the fields it gives and keeps those it leaves
  out (a pre-3.3 bundle names none), and writes a relation version, source
  IMPORT, only when it changed the relation.
- **Search** reads relation fields as a source of both ends (`relationField`,
  weighted as a relation note), within the relation read cap.
- **Prompts moved and their records were re-run**: `QUESTION_PROMPT`
  (`question-generation.3.3.0`, every pack record), `RECONCILE_PROMPT`
  (`reconcile.3.3.0`, enrichment cases en-41..en-44 and adversarial adv-15,
  adv-16) and the rephrase record (it shares the engine instructions). The
  output schema stays within 2.1's structured-output limits (every member
  required, one more nullable).
- **Not built here:** 4.3's relation-field generators; relation fields in the
  PDF export (the bundle has them); a relation field challenge mode.
